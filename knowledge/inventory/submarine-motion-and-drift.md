## 2. Доказанная цепочка: ветер → волна → скорость → позиция

sea.ProfilesManager.SetProfiles(waterProfilesBlend);
windDirectionTransform.localEulerAngles = new Vector3(0f, windDegrees, 0f);

В `uboat.scenes.main-scene`, serialized file

`W/PlayWay.Water/WindWaves.cs:438-457` читает `WindDirectionPointer.forward`,
нормирует X/Z и передаёт его в `spectrumResolver.SetWindDirection`.
Ранее оставленное «связь указателей недоказуема без запуска» отозвано:

### Волна содержит горизонтальную составляющую силы

`W/PlayWay.Water/WaterWave.cs:75-85`:

```csharp
float num4 = amplitude * num2; // num2 = sin фазы (таблица)
float num5 = amplitude * num3; // num3 = cos фазы
result.x += nkx * num4;
result.z += nky * num4;
result.y += num5;
result.w += num4;
```

Это raw sample спектра, ещё не ньютоны и не скорость течения.
`W/PlayWay.Water/Water.cs:592-600` берёт `GetForceAndHeightAt` из спектра;
`WaterSample.cs:283-309` учитывает локальную интенсивность волн и передаёт X/Y/Z;
`W/PlayWay.Water.Extensions/NeuralNetworkPhysics.cs:720,1219` получает эти силы
через `WaterSample(HeightAndForces)` для вокселей корпуса.

### Сила записывается в реальную скорость Rigidbody

`W/PlayWay.Water.Extensions/NeuralNetworkPhysics.cs:812,852,866-882`:

- начальная `a = rigidbody2.velocity`;
- `num28 = num18 * submergedVolumeFraction * wavesPart`;
- X/Z силы умножаются на `waveForcesHorizontalFactor`;
- коэффициент глубины =
  `exp(log(depthFade) * max(0, waterY - voxelY - 1))`;
- сила передаётся в собственный `AddForceAtPosition(ref a, ...)`.

Ветка NNP:870-882 асимметрична: при `waveForces.y < 0` весь вектор силы
(включая X/Z) применяется только при `num26 > 0.65`, дополнительно с весом
`(num26 - 0.65) / 0.35`. Иначе этот voxel-вклад пропущен. При неотрицательном Y
применяется обычный вес. Это проверенный нелинейный участок цепочки, **не**
доказанная причинным A/B единственная причина отрицательного среднего сноса.

**Важно:** это не только одноимённый вызов Unity и не декоративное движение mesh.
Собственный метод из **той же оригинальной DLL**, строки 1092-1106, выполняет:

```csharp
if (isFreezedY) force.y = 0f;
velocity.x += force.x * forceToVelocity;
velocity.y += force.y * forceToVelocity;
velocity.z += force.z * forceToVelocity;
```

В вызывающем коде `forceToVelocity = deltaTime / mass` (:785).
Затем сопротивление обрабатывает `a`, и :991 записывает
`rigidbody2.velocity = a / num38`. Здесь нет проекции всей скорости на нос.
В ветви без погружённой площади запись также идёт в Rigidbody (:1020).

### Боковая скорость не теряется при переносе на глобальную карту

`G/UBOAT.Game.Sandbox/SandboxPlayerWolfpack.cs:475-490` вызывает
`MoveToPlayerScenePosition(playerShip.RigidBody)` и берёт текущую позицию тела.
Сам метод :1515-1528:

```csharp
Vector3 scenePos = playerShipRigidBody.position;
position = SandboxGroup.sandbox.SceneToEncounterSpace(scenePos);
```

Вне PhysX есть и явный позиционный writer: при `ArtificialTimeScale > 1.001`
`ApplySpawnedUnitsSpeedupFactor` (:637-660) добавляет кораблям:

```csharp
component.position += component.velocity.MaskY(0f)
    * (1f - component.drag * Time.fixedDeltaTime)
    * Time.fixedDeltaTime * (gameTime.ArtificialTimeScale - 1f);
```

Здесь переносится **вся горизонтальная скорость**, не только её продольная
проекция. Это дополнительное доказательство связи X/Z скорости с положением.
Перескоки scene origin и navmesh snap нужно исключать из измерения дрейфа.

## 3. Исполнение оригинальной DLL: что доказано численно

`verify-drift.ps1` вызывает private static `NeuralNetworkPhysics.AddForceAtPosition`
из установленной DLL. Для изоляции линейной ветви вращение выключено, Rigidbody
передан null; native-сцена и полный `Execute` не запускаются.

Входы теста, **не параметры реальной лодки**:

- начальная скорость `(0,0,5)` м/с;
- сила `(1000,0,0)` Н, масса 10000 кг, шаг 0.02 с;
- фактический результат вызова DLL: `(0.002000000095,0,5)` м/с;
- противоположная сила даёт X = `-0.002000000095` м/с;
- нулевая сила даёт X = 0;
- `isFreezedY=true` убирает Y, но **не** X.

Это доказывает работающую боковую составляющую в алгоритме, но **не** количество
километров смещения лодки за час. Масса/сила теста заданы, а не сняты с кампании.

Вызван и оригинальный `WaterWave.GetForceAndHeightAt`: одна заданная волна
единичной амплитуды даёт raw X = +1 и -1 в разных фазах. Среднее 2048 фаз
`-1.0350936774372599e-10`, в пределах погрешности ноль. Следовательно,
мгновенные боковые силы нельзя подменять постоянной скоростью течения.
Это не доказательство нулевого среднего дрейфа корпуса: его движение и
нелинейные веса погружения в данном изолированном тесте отсутствуют.

### 5.1 Точки подмены для течения и ветра (проверено по IL)

- `Rudder.FixedUpdate` (:145-217) при `fullPhysics` берёт ровно две скорости:
  `-rigidBody.velocity` (:158) и продольную проекцию (:179). Обе — **мировые**;
  при течении воды поперечная сила руля должна считаться от
  `velocity - current`, иначе руль «видит» течение как ход.
- `Rudder.ApplyForce` (:219-250) — callback `NeuralNetworkPhysics`; его
  `velocity` приходит из той же мировой скорости (:221) и должен получать ту же
  относительную поправку. Замена только одного из двух путей оставляет
  расхождение между поворотом и торможением.
- Продольная составляющая `:179` также питает `averageVelocity` в `Ship.cs:1087`
  (low pass 0.012 за тик). Подмена только чтения руля не меняет показание хода;
  подмена `AverageVelocity` задела бы рули глубины и интерфейс.
- `Ship.Depth` (`G/UBOAT.Game.Scene.Entities/Ship.cs:194`) использует
  `currentWaterElevation`, поэтому экспозиция `Clamp01(-Depth)` применима и к
  неигровым корпусам, не только к `PlayableSubmarine`.
- Водная скорость для поправки берётся на глубине **верхней границы**
  корпуса (`Depth`, ≥0), не на поверхности и не на палубе. Мод
  `CurrentRuntimeAdapter` опрашивает профиль примерно 10 Гц вне шага
  drag; шаг физики использует последний отсчёт. Для ближних корпусов
  профиль опрашивается при обновлении их записи. Профиль задаётся
  `RADIONAV_CURRENT_PROFILE="глубина:восток,север;..."` и имеет приоритет
  над постоянным `RADIONAV_CURRENT_FIELD`; нулевой слой на глубине
  отключает поправку, но не означает «штиль в данных».
- Рантайм-потребитель атласа переводит мировую позицию корпуса через
  `Sandbox.SceneToEncounterSpace` и `Coordinates.ToLatLong` (км → градусы,
  окружность 40075.16 км), берёт кампанийный UTC из `GameTime.GmtDateTime`
  и глубину верхней границы корпуса. Западная долгота из игры проверяется
  также как `+360`, поэтому оси HYCOM 0…360 и −180…180 равнозначны.
  Отсутствие покрытия плитки означает отказ выборки, а не нулевое течение;
  битая плитка отключает адаптер, нулевая — не ставит патчи.

- `Ship.FixedUpdate` строит локальный вектор на текущий waypoint, затем
  применяет приоритет уклонения и берёт `Mathf.Atan2(x,z)` перед штатным
  регулятором руля (`Ship.cs:995–1067`). `PlayerShip.FixedUpdate` вызывает
  этот же метод. Подмена только угла оставляет сами точки, тягу и момент
  прохождения waypoint у игры. Для оценки достижимости на постоянном
  поле использовать `TargetVelocity` в м/с, не `AverageVelocity`
  относительно мира; `PlayerShip.ValidateTargetVelocity` выводит её
  из ожидаемого хода текущей передачи. Ускоренный `RotateBoatToWaypoint`
  в `SandboxPlayerWolfpack` — отдельный путь, не покрыт этой подменой.

- Дальняя группа: `SandboxMobileGroup.UpdateGroup` двигает
  `position += up * velocity * (StoryTicks - lastUpdateTime)`, где
  позиция — encounter-км, а `velocity` — км/с. Поле задано в м/с,
  поэтому сдвиг за интервал равен `water * seconds / 1000` в км.
  `lastUpdateTime` — приватное поле, но найдено в установленной
  обфусцированной DLL вместе с публичным `LastUpdateTicks`; метод
  `UpdateGroup` публичный, поэтому искать его нужно с
  `BindingFlags.Public`. `Position` — свойство: установка идёт через
  `SetPosition`, который пересчитывает `currentTargetDistance`, так что
  штатное прибытие продолжает работать. У группы, ещё ни разу не
  обновлявшейся, `lastUpdateTime == 0`: интервал получается
  CampaignAge и должен быть отвергнут, а не применён.

- Уведомление игроку: `UBOAT.Game.UI.INotificationBarUI` инжектируется
  по интерфейсу (`GetInstance<INotificationBarUI>()`), а
  `OpenNow(iconPath, localizedText)` принимает готовую строку без
  локализации и допускает пустой путь иконки. Текст подписи — приватное
  поле `TMP_Text` в `NotificationBarUI`, поэтому обратное чтение через
  `label.text` в обфусцированной DLL не работает; проверять показ надо
  по логу мода или визуально.
- Региональный срез ORA-20C: плитка 1°×1° с 5 уровнями и двумя
  месячными центрами занимает 260 B; предзагрузка четырёх плиток —
  единицы миллисекунд. Источник начинается с 5 м, поэтому запрос
  с поверхности даёт отказ покрытия, а не ноль. Поставляемые плитки —
  `Source/Data/CurrentAtlas/*.rnw` теперь являются расширенным атласом с
  явной реконструкцией 0 м (включается `RADIONAV_ATLAS_TILE=bundled`);
  провенанс и хеши — `Source/Data/CurrentAtlas/atlas.provenance.json`.
- `SandboxMobileGroup.UpdateGroup` интегрирует отдельное поле `position`;
  `Sandbox.Update` отдельно вызывает `Physics2D.Simulate`, а штатный
  `ValidateRigidBodyVelocity` пишет `up * velocity` в `rigidBody2D`.
  Поэтому мировую скорость образует сложение вектора тела с течением,
  а скаляр `Velocity` (маршрут, расход) менять нельзя.
- `DockArea.UndockRoute[0]` заполняется местом триггера в `RegisterRoute`.
  Указанная последовательность — из порта; обратная используется только
  после водного пути до входа. Пустой массив допустим. `WorldNavMesh.FindPath`
  возвращает статус и практически проверяется ещё по последней точке.
  Нативный `OnTriggerEnter` требует свободного места, союза и 15 игровых
  секунд в море; путь не заменяет постановку к причалу.
- Скорость ветра на карте — приватное `TextMeshProUGUI windSpeedLabel`
  в `MapUI`; её группа — `Wind speed Icon` → `Parameters` → `MapUI 2.0`.
  `MapUI.LateUpdate` читает `gameEnvironment.TotalWindSpeed` и
  `lastDisplayedWindSpeed`; округление для узлов прямое, для метрики
  `* 1.85166`. В проверочной кампании подпись читалась как `4 knots`,
  а выборка мода — 6.33 узла; причину устанавливать сравнением штатного

## 6. Границы результата и рекомендации для прокладки

- Доказана цепочка погодного ветра до горизонтальной скорости тела и его
  глобальной позиции. Это реальная физическая составляющая, не только UI/качка mesh.
- Не доказано число км/ч среднего ветрового сноса и его физическая точность.
  Нельзя применять процент скорости ветра или утверждать отсутствие накопленного
  переноса на основании среднего синуса при фиксированном sample.
- Штатную поправку на океаническое/приливное течение вводить не из чего.
  Поправку на устойчивый волновой перенос следует получать из измеренного
  движения, не из произвольного коэффициента ветра.
- `navigation-instrument-contracts.md:6,20-22` говорит о недостаточности
  показаний приборов, а не об отсутствии сноса. Менять этот контракт за это нельзя.
- Read-only обращение к игровому мосту в этом проходе вернуло WinError 10061.
  Игра не запускалась, погода/время/ход/сейвы не менялись. Полный in-game замер
  накопленного смещения этим отчётом не закрыт.

## 8. Направление волн измерено отдельно

## 9. Причина бокового сноса измерена контрфактами

`artifacts/reports/drift-causal-qa-20261115/` — причинный QA-разбор на том же
изолированном стенде, что и §7–§8, с наблюдателем вместо правки и отдельными
процессами на каждый контрфакт. Отчёт: `QA_REPORT.md` в том же каталоге.

Постановка контрфактов: Bft 5, курс 000°, 10 уз, 1 500 000 шагов
(19 999.999087 модельной секунды), штатные и Burst-ядра.

| Прогон | X, м |
|---|---:|
| `baseline` (наблюдатель) | −39.067814536544915 |
| `restore` (повтор исходного, побайтно тот же CSV) | −39.067814536544915 |
| `drag-torque-only` (снята поступательная часть advanced angular drag) | **+25.30799156213891** |
| `no-xz` (сняты силы волн X/Z) | **−86.73940342009371** |
| `no-xz-drag-torque-only` (сняты оба) | +4.082168640934128, vx ≡ 0 ровно |
| `ungate-xz` | +5.5454220904072145 |
| `no-depth-xz` | +371.9554916250205 |
| `direct-samples` (`sampleWaterDirectly=true`) | −127.31198066686864 |

Штатные (не Burst) ядра, 100 000 шагов: `baseline` −0.7910649993276593,
`drag-torque-only` +10.552267318144573, `no-xz-drag-torque-only`
+0.3022280135315898 (vx ≡ 0).

**Механизм:** отрицательный снос даёт не волновая сила, а поступательная часть
advanced angular drag. `NNP:1046` `a4 = Vector3.Cross(angularVelocity, lever)`,
`:1047` масштабирование `|a4| * num26 * angularDragPart`
(`angularDragPart = -0.5f * angularDragCoefficient * area * 998.6f`, `:1431`),
`:1059` `rigidbody2.AddForceAtPosition(a4, vector10)` — единственный вызов
`Rigidbody.AddForceAtPosition` в `Execute` (транспайлер падает, если их не 1).
Сила от качки корпуса уводит корпус против хода волн.

Разложение на записанной траектории (условный учёт, реконструкция скорости
сходится с точностью 4.4e-16 м/с): силы волн X/Z **+98.75297288693909 м**,
отложенная X-сила angular drag **−141.73892850088032 м**, смещение опорной
точки корпуса **+3.9181410773963137 м**, сумма = измеренный X.

По вращательным каналам (`Cross(ω,r).x = ω_y·r_z − ω_z·r_y`, деление точное,
один и тот же скаляр на оба слагаемых): канал рыскания **0.0 м**, канал крена
**−141.73892850088032 м** (совпадает с независимым разбором до 0.0 м).
Контрфакты: снятие канала крена даёт **+24.65510326410424 м**
(+63.72291780064916 м к контролю), снятие канала рыскания не меняет CSV
побайтно. Нулевой вклад канала рыскания — свойство стенда: курс задан
извне, `angularVelocity.y` обнуляется на каждом шаге, замеренный `max |ω_y| = 0`.

**Проверки измерений:** наблюдатель и расширенная телеметрия не меняют
траекторию (побайтно, SHA `b901d2846d6ba832…` и `b94e830aecac…`); A/B/A —
`baseline` = `restore` побайтно; замыкание баланса скорости на шаг 0.0 м/с;
остаток предсказания PhysX по измеренной силе ≤ 3.8e-8 м/с; при снятых обоих
писателях все боковые `dv` ровно 0 на 1 500 000 шагов; пересборка стенда из
архивных исходников дала CSV, побайтно равный эталону.

**Границы:** это стенд с заданными курсом и скоростью, а не кампания; в игре
корпус рыскает, поэтому канал `ω_y·r_z` не равен нулю и его вклад здесь не
измерен. Не доказано, что физика игры «неправильна»: измерен механизм в
контролируемой постановке. Признак сноса против волн не требует штормового
профиля (`no-storm`, 300 000 шагов: −14.28029302377621 м). Числа 1000-км
маршрута и контрфактов отличаются по длительности и состоянию шторма, знак и
порядок совпадают.

## 10. Суточный дрейф без тяги и без предписанных курса/скорости

`artifacts/reports/drift-engine-off-20261115/REPORT.md` — четыре новых
24-часовых опыта на исходных FFT/NN-ядрах установленных DLL, не экстраполяция
постановки с ходом 10 уз. Все шесть степеней свободы свободны, начальные
линейная/угловая скорости 0; винт, руль, якорь отсутствуют. Это компонентный
стенд без тяги, **не полная кампания с выключенным двигателем**.

Каждый случай: **6480001 шаг / 86400.00939048547 модельной секунды**.
Удаление от исходной точки по фактическим приращениям позиции корпуса:

| Вход selector / начальный курс | 6 ч, м | 24 ч, м | Максимум за сутки, м |
|---|---:|---:|---:|
| Bft1 / 000° | 190.150 | 503.239 | 503.239 |
| Bft3 / 000° | 149.185 | 552.818 | 552.818 |
| Bft5 / 000° | 277.438 | 473.431 | 474.474 |
| Bft5 / 090° | 214.016 | 339.509 | 340.467 |

**Ни 1 км, ни 2 км, ни 3 км удаления не достигнуты** — пороги проверялись
на каждом физическом шаге. Итоговые горизонтальные сдвиги центра масс
504.755 / 553.669 / 473.837 / 339.557 м подтверждают, что это не только качка
опорной точки корпуса.

Накопленный горизонтальный путь **1.986 / 7.941 / 17.953 / 18.369 км**
включает возвратные перемещения; **это не расстояние, на которое унесло лодку**.
Не выдавать путь 18.369 км за net-снос 18 км. Увеличение Bft не даёт здесь
монотонного роста net-сноса; одной реализации моря недостаточно для такого закона.

**Граница ускоренных ядер:** при свободном yaw исходная DLL и локальные
Burst FFT/NN дали разницу endpoint102.129м уже за100000шагов. Поэтому
суточные результаты получены **без обеих подмен**. Локальные shadow-сверки
не доказывают совпадение долгой свободной траектории. Повтор short stock
побайтно одинаков; первые регулярные строки суточных Bft5 h000/h090 побайтно
совпадают с соответствующими короткими native-прогонами.

Штилевой исходный контроль имеет стартовый переходный сдвиг около2.16м при
посадке корпуса, но после300с дополнительное net-смещение **0.0м** за оставшееся
окно. Проверки эксперимента: **68 preflight + 29 native-check + 46 long PASS**.

**Вывод:** без тяги снос на сотни метров за сутки измерен; несколько километров
в этих четырёх опытах **не подтверждены**. Это не доказательство невозможности
при большей длительности/других seed/загрузке/кампании. Океаническое течение
и отдельная аэродинамическая сила ветра не добавлялись. Направление основного
хода волн вдоль новых суток отдельно не снималось; старый direction-verdict
другого маршрута не переносится автоматически. Графики, CSV/логи/команды,
контракты свободного движения и SHA-256 — в каталоге отчёта.
### Источники прямого ветра и экспозиции

- `Weather.cs:653–657`: `TotalWindSpeed` в узлах смешивает базовый
  `WindSpeed` и локальный профиль шторма. Направление сцены —
  `windDirectionTransform.forward`: поле закрытое, поворот назначается в
  `UpdateWeatherFactors` (`:1023–1033`), тот же мировой вектор используется
  для глобального ветра рендера (`:1623–1629`).
- `PlayableSubmarine.cs:254–260`: `Depth` положительна под водой и
  измеряется к верхней границе корпуса/рубки с учётом ориентации и текущей
  поверхности. `Ship.DeckDepth` — глубина в другой точке; подменять
  `Depth` этим значением при проверке экспозиции нельзя.
- `Entity.cs:287,885–901`: `Entity.List` — реестр включённых компонентов,
  не реестр дальних групп. Для ближних объектов дополнительно проверять
  текущую привязку `SandboxEntity`: pooled-компонент может обслуживать
  другую сущность. `DockPoint.cs:83–103` при швартовке NPC кратко
  включает `isKinematic`, затем оставляет `RigidbodyConstraints.FreezeAll`
  и выключает кинематику. Одна проверка `isKinematic` недостаточна.
