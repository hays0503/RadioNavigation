# Линии положения на карте

Реализация 2026-11-12: выбран показ **обоих наборов**, исходного и перенесённого.

## Что рисуется

- После первого успешного `I` — линия положения №1, после следующих — №2/№3.
- Синие `LOP n O` — исходные линии из карточки 7b книги.
- Оранжевые `LOP n T` — параллельный перенос исходной линии на ход лодки
  к моменту последнего наблюдения серии.
- Если ход нулевой, совпадающие O/T не дублируются. Свежая подпись — `O=T`.
  После загрузки native-сейва подпись может быть просто `O`: это та же сохранённая
  линия, без попытки угадать удалённый пользователем второй набор.
- Каждая линия — отрезок длиной 40 морских миль, по 20 в обе стороны от точки
  линии. Это не окружность равных высот и не стороны треугольника.
- Номера соответствуют книге и слотам текущей серии, включая заменяемый третий.

Отрисовка использует `MapChartingUI.CreatePoint/CreateLine`, не `LineRenderer`
и не самостоятельный экранный overlay. Игра отвечает за проекцию, масштаб и
штатный вид пунктирной линии. Нативные endpoints доступны инструментам карты;
инструмент Points не переименовывает служебные ключи.

## Геометрия и ограничение точности

Исходные точки строятся через тот же `RunningFixCalculator.BuildLop`, что книга.
Направление линии перпендикулярно истинному азимуту, а не совпадает с ним.
Перенос выполняется через `TranslateLop` с курсом/скоростью, взятыми при `I`.
Скорость не перечитывается каждый кадр: линии не ползут вслед за лодкой.

Перенесённые линии — **первое приближение**, как блоки F1–F3 книги. Решатель FIX
затем уточняет касательные около нового места. Поэтому нарисованные O/T не
обязаны точно проходить через опубликованный FIX или вершины уточнённого
треугольника. Устаревшая скорость остаётся ограничением расчёта, не устраняется
отрисовкой. Вблизи полюсов/за границей допустимых геокоординат отрезок пропускается,
а не зажимается в неверную геометрию.

## События, удаление, сохранение

- Только успешный замер публикует новое построение. Отклонённое `I` его не меняет.
- Новое `I` заменяет только автолинии и endpoints этой серии.
- Менеджер линий при `O` убирает только свои объекты. FIX, вершины, маяки и
  пользовательские объекты не входят в ключи владения
  `RadioNav SIGHTLINE O1 A` … `T3 B`. Прежний сброс FIX/вершин самим worksheet
  при `O` остаётся без изменений.
- Если пользователь построил свою фигуру на служебном endpoint, при сбросе
  endpoint остаётся как `LOP anchor`, с тем же Data reference; фигура сохраняется.
- Стирание линии не вызывает её немедленного возрождения; публикация повторяется
  только при новом `I`. Текущий `MapShapeEraser` удаляет связанные фигуры через
  endpoint, сохраняя сам endpoint — прежний контракт карты не менялся.
- Native points/lines сохраняются в той же игровой `.save` вместе с остальными
  построениями. После загрузки они только принимаются и перекрашиваются,
  позиции не вычисляются заново и ручной drag сохраняется. Payload астронавигации
  остаётся v3. Старый сейв без таких линий не получает выдуманный перенос.
- Если карта/UI ещё не доступны, публикация ждёт их готовности; есть повтор
  раз в секунду и дополнительный flush перед сохранением. До успешного flush
  native-объектов ещё нет — не считать такой случай проверенным сохранением.
- Во время LoadingInitialization/Loaded обновление не трогает native-геометрию.

### Мерцание после замены материала (2026-11-12)

сообщил о дрожании. В PID 41376, RTX 4080 SUPER / D3D11, 1920×1080, неподвижная

Installed ShaderLab: `UI/Map (Route)` имеет фиксированный ZTest Always (8),

### Исполняемая регрессия адаптера по ревью 2026-11-14

`Dev/RadioNavigation.SourceCheck/LopMapSourceTests.cs` компилирует полный
`SextantLopMapLines.cs` и настоящие ownership-предикаты из SextantLopPlot;
Unity/native database заменены embedded fixtures, тела cleanup/material не
дублируются. Проверяются сохранение Data references пользовательских линий,
кругов, углов и bearing, переименование anchor, удаление только своих rows,
отложенный Destroy, исчезновение собственной UI-линии между сохранёнными anchors
и повторы после отказа при создании второго endpoint/уже зарегистрированной линии.

Материальный сценарий проходит через реальные TryReplace/Style/Apply/Bind и
TryAdopt: проверяет фактическое назначение отдельной копии, отсутствие повторной
аллокации при Apply/adopt, локальный depth=Always и освобождение вместе с Graphic,
без изменения shared default. Мутации, удаляющие referenced.Contains, owner.Bind,
graphic.material assignment или ограничение создания одной копии, обязаны ломать
сценарий. Это дополняет прежние binding-гейты, а не делает их пиксельным тестом.

В рамках ревью производственная очистка/материалы не менялись: подтверждён пробел
покрытия, а не найденный дефект этих тел. Native callbacks моделируются doubles;
живая приёмка pointer/save/load и реального Unity deferred lifecycle остаётся
отдельной. Команда: `dotnet run --project Dev/RadioNavigation.SourceCheck -c Release -- LopMap`.
