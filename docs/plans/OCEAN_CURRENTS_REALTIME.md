# Течения UBOAT: real-time профиль, хранение и стратегические события

Дата: **2026-11-16**. Дополнение к [плану](OCEAN_CURRENTS_PLAN.md) и
[реестру рисков](OCEAN_CURRENTS_RISKS.md), не замена F0–F9.
Исследование источников — [OCEAN_CURRENTS_DATA_RESEARCH.md](OCEAN_CURRENTS_DATA_RESEARCH.md).

**Статус: проектная записка и отчёт о синтетических измерениях. Реализация
течений в игре не начата.** Production `Source`, игра, сейвы, бандл и кампания
не менялись. Ни один результат ниже не является игровым FPS, кадровым p99 или
доказательством 60 FPS.

## 1. Приоритет и границы

Пользовательский приоритет: **не менее 60 FPS на среднем оборудовании**;
осознанные упрощения допустимы. 60 FPS — это 16.667 мс на весь кадр, а не
бюджет течений. Главный способ выиграть время: не решать океан в игре, не
распаковывать научные файлы в физическом шаге, не считать одну астрономию
тысячи раз и не пересчитывать весь атлас ради нескольких судов.

Рабочие цели ниже — **предложения**, а не доказанные характеристики:

- main-thread выборка + диспетчер поля: p99 ≤ 0.5 мс на rendered frame для
  стартового профиля; редкие пики > 1 мс — в отдельный журнал;
- горячая выборка: 0 B/query, без IO, decode, ожидания worker, LINQ, строк и
  исключений на обычном отсутствии данных;
- память атласа: 64 MiB устойчиво, 96 MiB пиково, включая старые снимки,
  строящиеся результаты, decoder scratch и очереди;
- среднее оборудование для будущего A/B: предварительно desktop класса
  Ryzen 5 3600 / Core i5-10400, 16 GiB RAM, SSD. Ryzen 9 7950X из текущего
  стенда **не заменяет** эту машину;
- если baseline уже медленнее 16.667 мс, микробенчмарк не докажет 60 FPS.
  Нужны baseline/feature A/B с разделением CPU/GPU и фиксированными настройками.

Запрещено выдавать за приёмку: synthetic p99, один удачный кадр, пустой
`Sample`, доставку команды без игрового постусловия или число групп из
таблицы ниже как реальный состав мира.

## 3. Хранение и формат

### 3.1 Офлайн, не в игре

NetCDF/xarray/PyFES и научные библиотеки остаются в сборщике атласа. В игру
поставляется проверенный версионированный бинарный пакет. Нельзя считать
месячное усреднение доказанным detiding; региональная модель **заменяет** фон
по правилу состава, а не прибавляется вторым полным полем.

Порядок: эталон float → компактный кандидат → ошибки векторов и траекторий
6/24/72 ч → допуск. Число глубин, разрешение и K не утверждаются только потому,
что стенд использовал D=4 и K=8/16/34.

### 3.2 Пакет

Один index/manifest и независимо читаемые блоки. Не JSON/SQLite/NetCDF на
каждую выборку. SQLite допустим как офлайн-каталог, но не даёт причины выполнять
SQL для четырёх узлов фиксированной сетки.

Манифест: magic/version/endian, проекция/оси/единицы, координаты и глубины,
calendar mapping, constituent identifiers и phase convention, layer ownership,
coverage/support, source/atlas hashes, max dimensions/decoded lengths, codec,
attribution, лицензии.

Данные:

- сезонный фон: east/north `int16`, flat `[season,depth,node,component]`;
  на горячем рабочем наборе достаточно двух соседних сезонных срезов, но весь
  обязательный coarse fallback может быть resident;
- баротропный прилив: отдельно по горизонтальным узлам `(a_u,b_u,a_v,b_v)` на
  constituent, не 4D-почасовые поля и не копия на каждой глубине. Это
  баротропное приближение, не произвольное затухание к дну;
- коэффициенты `a=A*cos(g)`, `b=A*sin(g)`. Интерполяция — в Cartesian, не
  напрямую phase: 359° и 1° нельзя усреднять в 180°, противоположные векторы
  должны сокращаться;
- `short.MinValue` зарезервирован для missing; отдельная availability. Маски
  учитывают глубину/компонент/сезон там, где поддержка различается. Один байт
  на узел в синтетике — fixture, не готовая маска реальных данных;
- round-to-nearest: скалярная ошибка ≤ scale/2; overflow отвергать, не
  обрезать; ошибка суммы гармоник больше ошибки одного коэффициента;
- halo/граничные узлы — из канонического представления; независимый per-tile
  scale не должен создавать разные края одного поля;
- FES barotropic tide хранится отдельно от 3D-фона; total/Stokes/detided не
  смешивать без правила владения слоем.

Компрессия: per-block raw либо raw-DEFLATE (framing указать явно), без внешней
зависимости как первый кандидат. Raw выбирать, если сжатие увеличивает размер
или не даёт полезного выигрыша. На синтетическом K34: raw **1,288,657 B**;
Framework Deflate Fastest **1,117,439 B**; CoreCLR **1,358,071 B**. Это
синтетическое соотношение, не свойство реального океана. `DeflateStream` есть
в .NET Standard 2.0; наличие и поведение в установленном Mono нужно проверить
отдельно. Atlas identity привязывать к decoded hash, не только к compressed blob.

Не загружать всё глобальное поле 1/36°/50 глубин. Иллюстративный прямоугольник
−90…45°E / 0…75°N, 12 seasons, 4 depths, K34, int16 и минимальная однобайтная
маска: 0.5° ≈ 18.15 MiB; 0.25° ≈ 72.21 MiB; 1/12° ≈ 647.68 MiB. Это арифметика
без land culling, halo и полной mask metadata, не выбранное разрешение.

### 3.3 Нижняя граница памяти плитки

Плитка 65×65 (4225 узлов), D=4, 2 seasons, K34, int16 coefficients, две
float32 tidal snapshots и минимальная маска:

```text
seasonal 4*N*D*S = 4*4225*4*2 = 135,200 B
tidal    8*N*K   = 8*4225*34 = 1,149,200 B
mask             = 4,225 B
snapshots 16*N   = 67,600 B
итого            = 1,356,225 B = 1.2934 MiB
```

16 плиток = **20.6944 MiB**; 32 = **41.3888 MiB**; old+new для 32 =
**82.7774 MiB** ещё без decoder/queues/full masks. «32 плитки в 64 MiB» при
полном double-buffering неверно. Это lower bound payload, не total heap.

## 4. Горячая выборка

1. На границе шага захватить immutable `AtlasSnapshot` + `TemporalBasis` + epoch.
2. Получить tile/cell cursor; переиспользовать индексы и угловые значения,
   пока не изменились tile/cell/depth bracket/version. Пересчитать веса при
   изменении дробных X/Y или глубины, даже внутри тех же ячейки и интервала.
3. Background: bilinear четыре узла, linear depth, linear seasonal anchors с
   корректным calendar mapping.
4. Tide: один общий temporal basis на distinct game timestamp, затем dot product
   коэффициентов. Никаких sin/cos в каждом объекте.
5. Вернуть struct `(u,v,availability,provenance)`, без изменения Rigidbody и
   позиции; без Unity API в worker.

Для временных весов аналогично: тот же интервал не означает ту же дробную дату.
При смене пары сезонных срезов или приливных опор обновить ссылки. Готовый
интерполированный результат пригоден только при неизменных входах его
интерполяции; равенства индексов недостаточно. Cursor инвалидируется при
смене ячейки, глубинного интервала или версии атласа; floating origin — только
через правильную глобальную конверсию. Строковые ключи, рефлексия, `FindObject`,
мутирующий LRU-словарь и `Task` на каждый `Sample` исключаются. Разные timestamps
стратегических групп нельзя насильно считать одной датой ради кеша.

Для физического судна в первой модели допустим один вектор воды на корпус, если
явно принят предел однородного потока. Приложение сил и интегрирование остаются
каждый physics step; редкая выборка поля не равна редкой физике. Потерю shear
torque нельзя скрывать.

## 5. Sparse и dense

- **Sparse** (далёкие группы, мало запросов на площадь): shared basis +
  интерполяция коэффициентов при `Sample`; не пересчитывать все 4225 узлов
  плитки ради одного судна. Кешировать угловые коэффициенты; интерполированные
  переиспользовать только при совпадении дробных координат, от которых они зависят.
- **Dense** (загруженная сцена, много повторных проб): заранее
  материализованные u/v на двух game-time anchors только нужных плиток.
  Горячая выборка O(1) по K; между anchors — линейная интерполяция по времени.
  Refresh O(nodes·K) оплачивается отдельно, дробно или в worker, со сроком
  готовности.

Условие окупаемости:

```text
reuse_queries * (cost_direct - cost_snapshot) > cost_refresh
```

Материализация на малой плотности может проиграть. int16 сам по себе не даёт
ускорения: выборка меньше памяти, но получает conversions/multiply; float-hot
cache может оказаться быстрее. Нужны измерения на Mono.

Для `u=A*cos(wt)` линейная ошибка anchors ≤ `A*w^2*h^2/8`, где h — **game
seconds**. Для M2, A=1 м/с: 60 с ≈ 8.89e-6 м/с; 900 с ≈ 0.002 м/с.
Использовать самый быстрый retained/inferred constituent, включая M4/M6/M8, а
не M2-only. При slack/cancellation сравнивать абсолютную ошибку, не проценты
от почти нуля. Формула с постоянной частотой не заменяет проверку исторических
nodal/astronomical factors.

Refresh не должен менять уже выданные snapshots. Проверенный v4-прототип
материализует в отдельные buffers; numeric preflight на workload 16 плиток ×
8192 запроса дал `snapshot_max=2.35765777183246e-06` при `bound_max=
2.0645255618080525e-05`; `packed_vs_float=0.0002023012` при bound
`0.0005167767`; shared-vs-per-object = 0. Это синтетика, не реальные маски.

## 6. Предпочтённый стартовый дизайн

**Проще, не async streaming по умолчанию:** preload небольшого coarse/theater
пакета в контролируемой loading boundary; обычная выборка через shared temporal
basis + coefficient/cursor arrays. Региональные/портовые блоки тоже preload,
если помещаются в бюджет. Async streaming и materialized tile snapshots —
расширения по измеренному объёму/crossover, не обязательный старт ради
искусственного stress 8192.

Startup loading не смешивать с gameplay-frame budget. В обычной физике не
должно быть `.Wait`, IO, decode или блокирующего lock. Один bounded loader или
конечное число workers, не Task на miss; дедупликация requests; bounded
pending/completed queues.

- read/decode/hash/validate вне physics; checked products/offsets; max decoded
  bytes до allocate; reject truncated/excess output;
- preflight/pin working set шага; prefetch учитывает remote groups и game-time
  travel, не только соседей игрока; teleport/load/skip — отдельная барьерная
  ветка;
- публикация candidate одной reference на main-thread boundary; проверить
  campaign generation/atlas hash/temporal epoch; arrays после публикации не
  мутируют;
- retired buffers не возвращать в pool до окончания readers; atomic reference
  exchange не делает содержимое array/dictionary безопасным автоматически;
- избегать полного clone карты на каждый publish: immutable tile handles +
  ограниченный directory snapshot. Считать old+new+scratch одновременно;
- readiness cache **не меняет океан**. Coarse fallback либо является
  определённой частью фиксированного gameplay profile, либо отсутствие required
  tile задерживает переход вне physics. Cold-cache одному кораблю и warm-cache
  соседу не должны давать разные океаны;
- quality profile выбирается явно, хранится в save/manifest; скрытое понижение
  K/разрешения по текущему FPS запрещено — иначе траектории зависят от машины.

### 6.1 Берег и глубина: карта применимости до расчёта течения

**Кандидат F4/F5.** Две карты выполняют разные роли: море модели течения
определяет применимость её чисел, а игровая геометрия — сушу, дно и реальные
ограничения движения. Не исправлять одну другой. План сборки пакета:

- Сопоставить координаты обеих карт и отсчёт глубины. Для каждого интервала
  глубин проверить обе компоненты воды и каждый слой, который участвует
  в итоговом поле. Баротропный слой сам по себе не разрешает глубинный
  профиль. При неизвестной геометрии или отступе от дна — `Unsupported`,
  не экстраполяция. Проверять лицензии до поставки растра или производных.
- Дешёвый начальный допуск: **вся область опоры интерполяции** гарантированно
  мокрая на обоих концах интервала глубин и между ними в обеих картах.
  Положительная глубина дна в центре или четыре мокрых угла этого не
  доказывают. Построение offline консервативно учитывает пересечение
  берегового полигона со всей областью (либо использует подтверждённые
  нижнюю/верхнюю границы глубины внутри исходных ячеек). Если исходных
  данных недостаточно, нельзя считать отсутствие маленькой суши доказанным.
- Нативный региональный набор может вернуть часть покрытия, если его
  собственная опора проходит ту же проверку. Дробление одной грубой ячейки
  на подячейки **не** делает её исходные коэффициенты независимыми и не
  восстанавливает её течение через сушу. Не брать ближайший мокрый узел на
  другом берегу, не перенормировать остаток весов и не проецировать любой
  вектор вдоль берега. Узкости, которых нет в источнике или которые не
  совпадают с игровой геометрией, остаются ограничением охвата.
- Подготовить явное пространственное правило выбора профиля. Приоритет
  уточнения фиксируется данными, а не готовностью плитки. В переходе между
  наборами проверить согласованность слоёв, швы, скорости, перенос и
  расход через контрольные сечения: мокрота и даже связность не доказывают
  сохранение водообмена. До проверок не обещать достоверный прилив у базы.

**Интерфейс горячей выборки.** Один неизменяемый снимок, координаты, глубина
и игровая эпоха → статус и вектор только при `Valid` (включая настоящий ноль).
`Land` и `BelowBottom` допустимы лишь при однозначной классификации всей
опорной зоны запроса; смешанная/недоказанная опора — `Unsupported`.
`Unavailable` (нужные данные не готовы) и `Corrupt` не меняют выбор профиля
и не означают штиль. Политика ограниченного режима выбирается до шага
обоими потребителями, а не спрятана в `Sample`. Ветер над надводной частью
не становится нулевым от отсутствия данных воды, но это не разрешение
молча продолжать полноценный совместный шаг с неизвестной водой.

**Быстрый формат для проверки.** Для ячейки и вертикального интервала:
плоский 32-битный дескриптор (`uniform status` или `mixed + индекс`),
один 32-байтовый блок на неоднородную запись (8×8 кодов по 4 бита).
Размер подячейки здесь — параметр стенда, не утверждённое разрешение.
Сначала проверить дескриптор и допустимость, только затем читать
коэффициенты и вычислять веса. Никаких `Raycast`, обхода связности, IO
или аллокаций на выборку; проверить индексы/длину буфера при загрузке.
Арифметика для 100 000 ячеек × 6 интервалов и 5% неоднородных записей —
**3,36 MB** против **19,20 MB** при 8×8 кодах в каждой записи. Это только
байты такого представления без таблиц атласа и аллокатора; с одним
равномерным статусом на ячейку возможен более дешёвый вариант.

**Траектория — отдельный контракт.** Статус точки не доказывает
безопасность всего интервала. Вдали от берега можно принять
консервативную огибающую траектории и глубины, целиком лежащую в
подтверждённой области. У ограничений — проверка пересечённых ячеек
с включением касаний и локализация первой границы применимости.
Хорда допустима только с доказанной огибающей ошибки изгиба и численных
погрешностей. Если огибающая не подтверждает область, уточнять в пределах
F3 либо не публиковать неподтверждённый участок (§9.6). Граница данных —
не столкновение с сушей: столкновение определяет игровой путь, а не
дыра CFD/атласа. В F8 отдельно замерять долю береговой ветви и хвосты
работы у базы, не выводить их из замера открытого моря.

`python Dev/CurrentAtlasPrototype/coastal_qa.py` — **16 PASS**: прямоугольники,
глубинный порог, статусы и индексация блоков. Не реальные берег/батиметрия,
связность проливов, траектории или измерение кадров.
Отдельная [сверка реальных векторных карт](OCEAN_CURRENTS_DATA_RESEARCH.md#measured-overlay-installed-uboat-vector-coast-vs-natural-earth-land)
нашла 1 ячейку в Гибралтаре и 8 на подходе к заливу Яде, где все четыре угла
мокрые в обеих картах, но полигон суши Natural Earth пересекает ячейку.
Это обосновывает проверку опоры, не подтверждает глубины и не закрывает F4.

**Глубина опоры без дополнительных проб в кадре.** Отдельная
[сверка установленного растра](OCEAN_CURRENTS_DATA_RESEARCH.md#measured-depth-support-in-the-installed-world-raster)
показала: в Гибралтаре на пороге 20 м центр ложно пропускает 43 из 392
тестовых ячеек, четыре угла — 2. Подготовка offline делит опору по границам
билинейных патчей исходного растра и берёт самое мелкое значение по всем
вершинам обрезанных патчей. Это точная граница только для такого
интерполянта. Игровой базовый растр не равен геометрии сцены; подводные
коллизии и проходимость остаются у движка, а расхождение с подтверждённым
игровым дном или неустановленный вертикальный отсчёт блокируют приёмку.

Для фиксированных узлов глубины результат записывается прямо в
статусы интервалов §6.1. Если понадобится общий численный потолок на
опору, вычитать обоснованный запас от самой мелкой глубины, округлять
**к меньшей глубине** и разрешать лишь `z_max < limit`, где `z_max` —
наибольшая глубина всей опоры, включая изменение глубины за шаг.
Численный порог не заменяет статусы слоёв: пригодность не обязана быть
монотонной по глубине. Ноль не допускает поверхность при строгом
сравнении, неизвестное хранится отдельным статусом.
В игровом шаге не открывать файл дна, не брать `Raycast` на объект и не
вводить отдельную оценку глубины для стратегической ветви. Такой фильтр
ограничивает воду, не меняет формулу ветра по экспозиции.

**Число уровней выбирать офлайн по векторной ошибке.** В
[срезах HYCOM](OCEAN_CURRENTS_DATA_RESEARCH.md#measured-velocity-mask-and-vertical-decimation-on-hycom-netcdf)
при переносе поверхностного вектора на глубину менялось даже направление.
Единый профиль из шести глубин дал ошибку до 0.463 м/с в Гибралтаре;
уплотнение снижало p95, но не улучшило max у Яде. Поэтому стартовый
кандидат — небольшой набор заранее выбранных профилей на регионы или
плитки. Один `profileId` и таблица интервалов по глубине вместо прохода по
всем уровням. При `Sample` читаются только два опорных уровня, а веса
вычисляются для текущей глубины, даже если интервал не сменился.
Разные профили на шве требуют общей вертикальной опоры или явного
ограничения; оба владельца движения читают один профиль.

Оценивать покрытие и p95/max на **одинаковых** контрольных запросах,
отдельно считать новые/потерянные допустимые запросы. При слабом течении
сравнивать абсолютные ошибки, при заметном — ещё и направление.
Выбирать уровень уплотнения на одних данных, принимать на независимых
периодах и по траекториям F4/F5. Если ошибки или покрытие за пределами
допуска — оставить нативные уровни в нужном интервале либо пометить
ограниченный регион; не заменять глубину поверхностным вектором.
Дополнительные уровни растят память и могут ухудшать кеширование, даже
если число чтений на запрос постоянно: измерять совместно воду и ветер
в F8. Профиль зависит от данных, не от текущего FPS.

### 6.2 Швы профилей: один вертикальный след на общем узле

**Кандидат для соседних плиток одного физического поля.** Близкие значения
в общих глубинных узлах ещё не дают непрерывности между ними. Если одна
плитка на границе хранит `0/100/200`, а другая — ещё и `125/150`, их
линейные интерполянты на общем ребре могут различаться при том же `z`.
Усреднение двух выборок скрывает скачок, но добавляет стоимость и не
сохраняет автоматически расход.

- **Один канонический след на горизонтальный узел:** offline выбрать
  вертикальные уровни (плотнее там, где нужно), общую маску и схему
  квантования. Две смежные ячейки ссылаются на тот же `nodeId` либо на
  его идентичную байтовую копию, включая масштаб, эпоху и состав слоёв.
  Для приливов копировать декартовы коэффициенты и применять ту же basis
  в той же временной системе, не перепаковывать уже округлённые значения.
  Углы четырёх плиток тоже имеют одного владельца. Ключ/выбор ячейки
  детерминирован в глобальных координатах, не зависит от floating origin
  или от того, какая плитка загрузилась первой.
- **Выборка:** в ячейке с общим профилем оставить быстрый путь — один
  поиск глубинного интервала, те же восемь опорных векторов. В смешанной
  ячейке сначала вычислить вертикальный след для каждого из четырёх
  углов, затем билинейно интерполировать горизонталь. Не более четырёх
  поисков и восьми опорных векторов на пространственную выборку при одной
  временной базе; нативный поиск ограничен числом уровней. Дорогой расчёт
  на стыке двух тайлов и усреднение результатов двух `Sample` не нужны.
  Кешировать ключи/индексы и углы, не фиксировать веса после движения.
- **Условие непрерывности:** обе ячейки допустимы, у них совпадает
  геометрия ребра и координата вдоль него. Тогда формула на ребре зависит
  только от двух общих узлов, одинаковых с обеих сторон. Это непрерывность
  значения, не градиента. Если весь шаг/ячейка не поддерживается, общая
  величина на ребре не отменяет отказ. Поддержку границы явно проверить
  офлайн; запрещено считать сухие/отсутствующие узлы валидными только
  из-за нулевого веса на ребре.
- **Разные продукты или горизонтальное разрешение:** сначала собрать
  согласованную полосу offline с совместимой физической семантикой,
  общей геометрией опоры и проверкой расхода/траекторий. В первой версии
  непроверенный шов исключить, не склеивать два независимых океана.
  Синтетический контроль: плавная смесь двух постоянных восточных
  потоков 0.4 и 0.8 м/с через сечение 1000 м² даёт разницу расходов
  **400 м³/с**, хотя скорость непрерывна. Это не прогноз для пролива.

**Стоимость измерить отдельно.** Сплошные плитки сохраняют простой
layout, смешанные ячейки — отдельный ряд дескрипторов. Иллюстративные
100 000 ячеек × 5% × (4 индекса `uint32`) = **80 000 B** только на эти
индексы, без директории, коэффициентов, масок, halo и heap. В F5 сравнить
общий профиль с редкими смешанными ячейками по байтам и скорости.
В F8 добавить проход вдоль шва и пакет запросов к смешанной полосе
(холодный/тёплый кеш при фиксированном профиле), отдельно учитывать
долю смешанных выборок; бюджет всё ещё общий для воды и ветра.
Большой процент смешанных ячеек — повод укрупнить зоны профиля или
выбрать единый профиль с проверенными допусками, не переключаться по FPS.

**Стенд:** `python Dev/CurrentAtlasPrototype/CoastCompare/seam_qa.py`
— 10 PASS; с `--input-dir <NetCDF-срезы>` дополнительно сравнивает профили
на потенциальных узлах стыка в реальном [свидетеле HYCOM](OCEAN_CURRENTS_DATA_RESEARCH.md#measured-velocity-mask-and-vertical-decimation-on-hycom-netcdf).
В Гибралтаре расхождение на одном узле двух профилей достигает 0.463 м/с.
Это верхнее наблюдаемое расхождение для этих выборок, не фактический шов
игры. В режиме общего следа непрерывность проверена в синтетических
смежных ячейках; отчёт HYCOM измеряет ошибку кандидата на каноническую
кривую лишь в узлах, не ошибку интерполяции полосы в пространстве.

## 7. Время: целое, double и игровые часы

Приливные фазы считать от календарного GMT игры, не от `LocalDateTime` и не от
`DateTime.UtcNow`. `GameTime.GmtDateTime` имеет `Unspecified`; не преобразовывать
его как локальное время компьютера.

- Внутреннее время — целые ticks либо `long`/`double` секунды с явной эпохой;
  float для накопленного времени не использовать.
- Различать ticks, story ticks, `ArtificialTimeScale`, `PhysicsTimeScale` и
  реальные секунды. Throttling по real seconds нарушает приливную фазу при TC:
  для compression `s` интервал `r` реальных секунд покрывает ≈`s*r` игровых;
  ошибка линейной интерполяции растёт как квадрат этого интервала.
- Валидность basis выбирать по game-time и самому быстрому retained constituent,
  а не по FPS. Фиксированные real-second throttles допустимы для UI/telemetry.
- Быстрые волны M4/M6/M8 и inferred waves могут доминировать над M2. Для шага
  `h` частоты `f` и `f+n/h` дают одинаковые samples; `h < 1/(2*f_max)` —
  необходимое band-limited условие, но не цель точности. Выбирать шаг по
  error budget; универсальных «1 минута» или «1 Hz» нет.
- Месячные средние не являются идеальным anti-alias фильтром; box mean
  ослабляет синусоиду на `sin(ωH/2)/(ωH/2)`, не обязательно до нуля.

## 8. Точный временной интеграл гармоники

Для фиксированных пространственных коэффициентов, frozen nodal terms и
постоянных частот:

```text
integral[a*cos(w*t)+b*sin(w*t)] dt
  = 2*sin(w*dt/2)/w * [a*cos(w*(t0+dt/2)) + b*sin(w*(t0+dt/2))]
```

Это дешёвый **точный интеграл поля воды в фиксированной точке**, не интеграл
скорости корпуса. Для кинематической ветви с заданным ходом относительно
воды его можно использовать лишь при доказанной применимости вдоль всей
траектории. Ветвям с инерцией, тягой или регулятором нужен интеграл мировой
скорости корпуса. Интегральный basis готовится один раз на общий интервал.
Для реального FES basis нужна независимая численная проверка/anchors.

Ограничения: движущаяся позиция, глубина, маршрут, маска, nodal changes и швы
требуют controlled spatial/event subdivision. Пространственная изменчивость
добавляет along-track частоту `V/L`. Одна правильная мгновенная вода не равна
правильному переносу за пропущенный интервал. Точная первообразная не заменяет
поиск событий внутри интервала.

Контрпример, не игра: чистая M2 1 м/с за полный период имеет net displacement
≈0, тогда как frozen start даёт 44.714 км; одна midpoint-выборка за полный
период даёт −44.714 км. Переход с Euler на один midpoint при огромном skip сам
по себе проблему не решает.

### 8.1 Начальный подшаг: локальная оценка, не гарантия траектории

При замороженных пространственных коэффициентах пропущенное смещение на
сегменте ограничено

```text
(V*h^2/2) * sum_k [L_a,k*P_k + L_b,k*Q_k]
```

при условии, что градиенты и предел скорости `V` справедливы на всём сегменте.
Для равных шагов `h` сумма **локальных вкладов** за время `T` — не больше
`T*V*h*L/2`, где `L` — сумма взвешенных градиентов. Это не граница конечной
ошибки: каждый шаг стартует уже со смещённой позиции. Для `V=1 м/с`, `T=24 ч`:

| L, (м/с)/м | смысл | начальный h, сумма 100 м | начальный h, сумма 10 м |
|---:|---|---:|---:|
| 1e-6 | 1 м/с на 1000 км | ~2315 с | ~231 с |
| 1e-5 | 1 м/с на 100 км | ~231 с | ~23 с |
| 1e-4 | 1 м/с на 10 км | ~23 с | ~2.3 с |

Контрпример: `x' = 1 + 10⁻⁵(x−t)`, `x(0)=0`, в СИ, точное решение `x=t`.
Точный по времени шаг с замороженной позицией даёт
`e_next=(1+10⁻⁵·h)e−10⁻⁵·h²/2`. При шаге ≈231 с за сутки сумма этих
локальных дефектов ≈100 м, но конечная ошибка ≈158 м. Это синтетический тест,
не измерение атласа.

**Решение:** использовать оценку для выбора первого кандидата на подшаг;
ограничивать его по геометрии, событиям и временной изменчивости. Допуск
траектории, включая ошибки по пути, проверять по уточнённому эталону на
6/24/72 ч; уменьшать шаг при непрохождении. Обещать строгую границу можно
только после учёта усиления ошибки (например, с сертифицированным глобальным
Lipschitz bound вдоль разрешённого участка). Таблица сама по себе не
разрешает пропуск подшагов.

## 9. События, alias и ограниченная работа

### 9.1 Внутреннее пересечение

Скалярный single-cosine fixture: `x0=0`, target 5000 м, первое пересечение
**5544.0019 с** (1.54 ч), хотя `x` за полный период возвращается ≈0. Проверка
только в конце интервала `(start-target)*(end-target)>0` его **не видит**.
Прототип ограниченного поиска: **9/9 PASS**, chunk 1/8 invariant, root bracket
переживает pause, событие обработано один раз; но это только scalar
single-cosine с аналитически известными turning points, **не общий coastal/
multi-harmonic locator**.

### 9.2 Alias в adaptive step-doubling

`x'=cos(2πt/44714.16)`, `h=4T` (49.6824 ч). Midpoint и RK4 на одном полном и
двух половинных шагах видят одинаковые фазы: step-doubling estimator = 0 и
принимает шаг при budget 0.25 м, но выдаёт **178,856.64 м** вместо ≈0;
абсолютная ошибка ≈178.857 км. Значит adaptive tolerance/step-doubling без
независимого temporal max-step или аналитического интеграла **не защищает** от
aliasing при time compression. Это ограничение estimator, не основание
отключать RK.

### 9.3 Scalar affine fixture

46/46 PASS на трёх fixture (diverging, converging, strong-gradient). Adaptive
endpoint errors **0.024 / 0.013 / 0.167 м** при **193 / 194 / 401** attempts
вместо 86,400 one-second steps; все интервалы **86,400 с**. Первые два
начинаются на t=1234 с и заканчиваются на t=87,634 с. Это скалярная affine
модель, **не 2D bilinear море**, не hull, не Unity.

### 9.4 Batch событий

Синтетика: 6 событий расположены плотно. Naive batch и «остановиться один раз
на границе большого segment» обрабатывают 1 и теряют 5; subdivision до первого
события/малого диапазона обрабатывает 6 и теряет 0. Инвариант: до commit ни одно
промежуточное событие не должно остаться необработанным. При плотных событиях
возможен load/TC cap, но не скрытый batch.

### 9.5 Трилемма и явный fallback

Нельзя одновременно гарантировать: (а) bounded frame, (б) отсутствие потерь
событий, (в) неограниченный TC/число групп. Явный fallback:

1. остановиться **до** ближайшего события, закоммитить только безопасную часть;
2. выполнить bounded catch-up barrier **вне физики** до зависящих событий;
3. при исчерпании бюджета — TC cap/backpressure и явный статус, а не тихий
   drop, stale encounter или «догоним позже» без следа.

Никогда не выдавать background backlog за актуальное состояние обнаружения и не
удалять событие ради FPS без записанного решения.

### 9.6 Кандидат: подготовка интервала по кадрам, единая публикация

**Проект, не найденный игровой hook.** Хранить отдельно запрошенную эпоху,
последнюю опубликованную эпоху и приватный курсор работы. Курсор привязан к
владельцу/поколению групп и снимку полей, команд и маршрутов. Подготовка ничего
не меняет в доступных игре позициях, часах или событиях.

1. Выбрать кандидатную эпоху по запросу, F3 max-step и срокам групп. Искать
   ранние события среди **всех влияющих групп и источников**; поздний результат
   первой обработанной группы не даёт права коммитить её вперёд остальных.
   Если поиск не доказал отсутствие более раннего события, эпоху не публиковать.
2. Подготовить движения только до минимальной подтверждённой эпохи. Обычный
   обход не подтягивает весь мир: включать группы с наступившим сроком F3,
   зависимости событий и кандидатов широкого поиска встречи. Пропуск группы
   безопасен лишь при доказанной границе для поиска и сохранении её долга.
   Если круг зависимостей ещё не доказан — меньший поддерживаемый сценарий,
   не предположение «далеко значит не влияет».
3. При событии применить эффекты в подтверждённом игровом порядке для этой
   эпохи. Поздние кандидаты, затронутые эффектами, пересчитать из нового
   состояния. Пример: остановка/замедление одной группы меняет ETA другой.
   Равные ticks требуют порядка штатного движка, не сортировки просто по ID.
   Каскад событий в одних ticks ограничивается бюджетом на подготовку, но
   не обрезается. Если нельзя подготовить его без действий с необратимыми
   эффектами, это блокер для такого режима, а не повод проиграть callbacks дважды.
4. Публиковать снимок и эпоху в согласованной точке до зависимых потребителей.
   Для своих данных — кандидат на два заранее выделенных буфера с публикацией
   версии. Подмена ссылки **не** обновляет Rigidbody/индексы/очереди игры.
   Для штатных потребителей F0/F3 должны доказать, что пакет применения
   ограничен по стоимости и никому не виден наполовину. Если это невозможно,
   не откладывать отставшую синхронизацию в обход barrier.

**Бюджет.** Проводить работу вне physics step. Учитывать отдельно поиск,
интегрирование, обработку событий и публикацию; лимит запросов к атласу не
ограничивает размер очереди или стоимость одного callback. Проверять лимит
до следующей ограниченной единицы работы, при исчерпании оставить курсор на
следующий кадр. Записывать abort/restart и причины при смене поколений или
входных данных. Не позволять незавершённому запросу заново потреблять стартовый
кусок каждый кадр; непрерывные инвалидации требуют явного TC cap или отказа.
Бюджет в миллисекундах, debt и критерии F8 §11.1 обязательны даже при cap
единиц работы. Никакого ожидания worker под physics/Unity callbacks.

**Проверка осуществимости.** `SimulateTicks` продвигает штатные часы и
обслуживает date/timed updates **до** `TicksSimulated` (§10). Нельзя
начислить задним числом новые движения и назвать это barrier. Сначала
найти точку до продвижения часов либо штатный путь с допустимыми короткими
порциями и проверить, что разбиение сохраняет порядок очередей, RNG, physics
и датирование событий: это не предполагается автоматически. Если baseline
или новый режим не проходят F8, длинный пропуск не принят.

**Синтетический стенд:** `python Dev/CurrentAtlasPrototype/scheduler_qa.py`,
**12 PASS**. Движение прямолинейное, игровые ticks целые, все группы due,
правила событий упрощены. На `t=3` два события публикуются вместе; первое
замедляет ещё не прибывшую группу и меняет её прежнее прибытие с `t=5`
на `t=7`. Разный бюджет кадров и размер окна подготовки дают один финал;
до публикации нет видимых частичных изменений. Нагрузка: 200 групп, 1202
условные единицы, cap 32, 38 вызовов кадра. Копии tuple и эффекты в этом
Python стенде не ограничены по времени; это проверка последовательности,
**не** benchmark FPS, планировщика Unity или настоящих каскадов.

## 10. Стратегический мир: статически прочитанный порядок игры

**ИСТОЧНИК ПРОЧИТАН, не игровой прогон.** `GameTime.SimulateTicks`
(`UBOAT.Game.Core.Time/GameTime.cs:421-501`) — цикл по chunks. В каждом chunk:
ticksBeingSimulated/storyTicks/storyTicksDelta (:452-455) → executionQueue
GameTicks/StoryTicks = TOD cycle date (:456-460) → nearby-group Unspawn
(:461-490) → RunDateUpdates (:491) → RunTimedUpdates (:492) →
`Sandbox.UpdateGroups` (:493) → LaunchEvents (:494) → `Physics2D.Simulate(num*1e-7f)`
(:496) → **единственный** агрегатный `TicksSimulated.Invoke(num)` (:497), один
раз на chunk.

Размеры chunk (:429-447): 30 суток (Low precision или остаток >60 суток), 12 ч
(>3 суток), 5 ч (Medium), 3 ч/1 ч/30 мин/остаток (High).

Следствия:

- группы, AI, date/timed listeners и физика коммитятся **до** aggregate notifier;
  мод, слушающий только `TicksSimulated`, видит уже совершённое состояние;
- обычный не-доковый time skip (`SkipTimeUI.cs:319-353`, SimulateTravel) **не
  вызывает** `SimulateTicks`: он ставит TimeCompression и уступает по кадрам,
  поэтому `TicksSimulated` не поднимается вовсе. Доковый skip использует
  `SimulateTicksLive` (`SkipTimeUI.cs:275` → `GameTime.cs:587-636`). За один вызов:
  `min(остаток, 24 ч + время до ближайших 11:00 по ветке :600) + 10 ticks`;
  при старте в 12:00 и достаточном остатке это **47 ч + 10 ticks**:
  девять чанков по 5 ч и последний 2 ч + 10 ticks. Интервал таймера ~2 реальных
  секунд не ограничивает длительность синхронного вызова. Дизайн не может предполагать,
  что hook `TicksSimulated` покрывает обычное сжатие времени;
- encounter может полностью разрешиться внутри chunk: `EncounterSimulator.
  ParseNextTurn` — timed listener (`EncounterSimulator.cs:388`), идёт на :492,
  крутит turns по 35 simulated seconds (:619-645) и может SendSummaryMessage/
  Dispose/RemoveEntity (:627-632,665-693) до notifier. `RunTimedUpdates`
  опустошает очередь и переносит reschedule на ticks+interval
  (`ExecutionQueue.cs:586-593`), не покадровый catch-up;
- unspawned group (`SandboxMobileGroup.UpdateGroup:429-492`):
  `delta=StoryTicks-lastUpdateTime` (:432-439), применяется **одним** jump
  `velocity*dt` (:466-483). При достижении target позиция **точно** ставится в
  `route[0]`, fuel уменьшается, `Route.RemoveAt(0)` (:467-478), overshoot
  **отбрасывается**; цикла по waypoint нет. `lastUpdateTime=storyTicks`
  выставляется **до** move (:439), поэтому повторный вызов в том же chunk даёт
  нулевой delta. Итог: не более одного waypoint за chunk; current-induced или
  быстрый overshoot молча съедается на каждом arrival;
- arrival датируется концом chunk: `CurrentDateTime => new DateTime(storyTicks)`
  (:224) после :454;
- `Route.RemoveAt` синхронно поднимает `Changed` (`Route.cs:810-818`; event
  :171) → `Route_Changed` (`SandboxMobileGroup.cs:661-702`) пересчитывает
  `currentTargetDistance` и заново ставит date listener на
  `CurrentDateTime+currentTargetDistance/velocity` (:679). Date listeners
  массово дренируются против **фиксированного chunk-end tick** без продвижения
  времени между callbacks (`ExecutionQueue.cs:440-446`): много arrivals
  срабатывают подряд с одной и той же датой;
- multi-waypoint consumption есть только у групп, заспавненных во время skip:
  `MoveAlongPath(ticks)` (`SandboxMobileGroup.cs:399-427`) от
  `TicksBeingSimulated*Random.value` (`GroupSpawner.cs:1319-1329`,
  `CustomGroupsController.cs:168-175`), рекурсивно по waypoint, с одним
  `Changed` на каждый;
- observation suppression: `allowObservationUpdates=false` для 30d/12h/Medium
  chunks (`GameTime.cs:429-447`); `SandboxGroup.UpdateGroupLowFrequency` только
  `RemoveOutdatedObservations` вместо `UpdateObservations`
  (`SandboxGroup.cs:1526-1563,1788-1827,2273-2286`). Новых «group spotted» внутри
  таких chunks не возникает;
- spawned groups: route sync из `ship.transform` — `SandboxMobileGroup.cs:445-457`,
  то есть на :493 **до** `Physics2D.Simulate` (:496); waypoint/arrival chunk N
  выведены из физики chunk N−1. `Route.Update(Vector2)` может потребить несколько
  waypoint в while-цикле (`Route.cs:417-452`), поэтому несколько TargetReached
  могут сработать в одном вызове.

**Поправка к прежней формулировке:** не писать «события накапливаются только в
конце segment». События синхронные; верно то, что они штампуются chunk-end датой,
промежуточные участки unspawned group не эмитятся (one-waypoint cap + отброшенный
overshoot), а aggregate notifier срабатывает один раз после всего.

### 10.1 LIVE cadence не равна «каждая группа каждый кадр»

`Sandbox.Update` (`Sandbox.cs:1115-1181`): wolfpack (:1129); затем round-robin
batch групп (:1130-1142), где
`updatesCount += groups.Count*min(0.25f, dt*ArtificialTimeScale/I)`,
где `dt = Time.deltaTime` (уже масштабирован Unity), а
`I = lowFrequencyUpdateInterval * ExplorationScale / SandboxTimeScale`;
floor ≥1 (:1121-1128, default interval 30, :60); `UpdateGroupLowFrequency` первым,
`UpdateGroup` — только для `!DetectedByPlayer && NotSpawned`; затем все observed
(:1143-1155); затем все nearby (:1156-1163); затем Physics2D accumulator
(:1164-1180). Во время skip `Sandbox.UpdateGroups` (:1183-1190) прогоняет **все**
группы один раз за chunk с обоими вызовами.

Следствие: мод обязан интегрировать current за **собственный** elapsed ticks
группы, не за глобальный frame delta, и не предполагать равномерный cadence
между live и skip.

Арифметика (не измерение игры): `groups=8192`, 60 кадров/с,
`dt = TC/60`, `ArtificialTimeScale=ExplorationScale=SandboxTimeScale=1`,
`lowFrequencyUpdateInterval=30`:

| TC | groups/frame | sweep | game seconds на группу за sweep |
|---:|---:|---:|---:|
| 1 | 4.6 | 30 с | ~30 |
| 10 | 45.5 | 3 с | ~30 |
| 140 | 637.2 | 0.214 с | ~30 |
| 450 | 2048 (cap first binds) | 0.067 с | ~30 |
| 1000 | 2048 (cap) | 0.067 с | ~66.7 |
| 10000 | 2048 (cap) | 0.067 с | ~666.7 |

В этом примере порог 450× и ~30 игровых секунд ниже него — не контракт игры.
В общем случае cap срабатывает при `dt*ArtificialTimeScale >= 0.25*I`, а
`GameTime.cs:639–648` задаёт прирост StoryTicks через `dt*ArtificialTimeScale*SandboxTimeScale`.
Оценка интервала одного полного обхода — максимум из
`lowFrequencyUpdateInterval*ExplorationScale` и `4*dt*ArtificialTimeScale*SandboxTimeScale`,
без учёта принудительного минимума в одну группу, округления, внеочередных
вызовов и смены масштаба. Для интегрирования читать фактический интервал.

### 10.2 Arrival, destroy и listeners

- Arrival geometry — **half-plane**, не конус: `Route.Update`
  (`Route.cs:402-461`) проверяет `initialDirectionToWaypoint · (waypoint-position)
  <= 0` (:428), затем дренирует только совпадающие дубликаты `sqrMagnitude<1E-10`
  (:431-434). Углового/bearing tolerance в файле нет; target-following routes —
  радиальный 0.01f test (:441-447). Spawned ship private route — тот же line test
  в `EntityRoute.Update` (:353-369) из `Ship.Update` (:757/761). Снос, пересёкший
  плоскость waypoint за километры сбоку, всё равно считается arrival.
- Завершение route уничтожает/швартует группу: `ConvoyBehaviour.OnBehaviourUpdate`
  (`ConvoyBehaviour.cs:77-108`): `Route.Count==0` → per entity `SandboxDock.TryDock`
  либо `Destroy(returnToPool:true)` (:84-100), затем `Object.Destroy(group.gameObject)`
  (:101) безусловно от spawn state. `ReturnToPortBehaviour` (:127-179): только
  при `Route.Count==0 AND (SpawnState <= SpawnedImpostors || !Spotted)` —
  AddAircraft/TryDock/destroy entities (:142-166), затем Destroy group (:167);
  если spawned AND spotted, ветка пропускается и группа может остаться с пустым
  route. Удаление идёт через `OnDestroy` → `Sandbox.RemoveGroup`
  (`SandboxGroup.cs:903-908`; `Sandbox.cs:1034-1048`); Destroy отложен, поэтому
  удаление внутри for-loop `UpdateGroups` (:1185-1189, без null check) не меняет
  список на ходу.
- Pending date listeners **очищаются** на переходах состояния:
  `ExecutionQueue.GameState_StateChanged` чистит все pending date listeners на
  Running и Quitting (`ExecutionQueue.cs:635-652`). Arrival listeners заново
  ставятся `Route_Changed`/velocity set (`SandboxMobileGroup.cs:109,679`).
  `lastUpdateTime` (decl :43) переинициализируется `StartGroup` (:174), который
  вызывает `Sandbox.AddGroup` (`Sandbox.cs:1015-1029`). Модовый catch-up/arrival
  должен переживать save/load переarm'ом из persisted state, а не очередью.
- Encounters не являются date-listener driven: 2D triggers
  (`SandboxGroup.cs:2356-2384`), wolfpack proximity/state
  (`SandboxPlayerWolfpack.cs:515-570,692-820,1534-1568` в FixedUpdate/Update),
  turn-based `EncounterSimulator` timed listener (:584-651, reschedule
  35f/entities.Count, burns turns while `TicksBeingSimulated>0` :619-645).
  Поскольку `SimulateTicks` — один синхронный цикл внутри кадра, Unity
  Update/FixedUpdate wolfpack не может вклиниться; hard-encounter
  `DetermineEncounterMode` оценивается только после возврата skip.

### 10.3 Открытые вопросы по исходникам

Не выдавать за факты: `NextTimeSkipStoppingDateListenerTicks`
(`ExecutionQueue.cs:189-204`) не имеет найденного reader; `Region.Speedup`
применяется в `MoveAlongPath` (:404), но не в `UpdateGroup` (:466) и не в
listener ETA (:109,:679) — intent не подтверждён; последствие
`Physics2D.Simulate` с chunk-sized dt (до 30 суток) для Rigidbody2D **не
измерялось**; abort-проверка `SkipTimeUI` смотрит только spawned Observators в
`wolfpack.NearbyGroups` (`SkipTimeUI.cs:321-338`), покрытие unspawned/air не
подтверждено; входит ли wolfpack игрока в список `Sandbox.UpdateGroups`, не
подтверждено; у `TicksSimulated` нет re-entrancy guard; порядок исполнения
`ExecutionQueueListener`/`GameTime.Update`/`Sandbox.Update` задаётся сценой, не
кодом, поэтому в live play `RunDateUpdates` может использовать story ticks
предыдущего кадра; сохранность `lastUpdateTime` через save/load не прослежена
дальше `StartGroup` re-init; часть data-driven Sandbox/Settings/Travel значений
не прочитана.

### 10.4 Вывод для владения интервалом

Позиционная перезапись current здесь хрупка: она может быть зажата в `route[0]`,
посчитана от chunk-end даты или применена на неравномерном live cadence. Current
должен входить как **owned interval contribution** с per-group elapsed ticks и
явным правилом overshoot/arrival. Игра уже интегрирует каждую группу за её
собственный `StoryTicks-lastUpdateTime`; мод должен потреблять этот же интервал,
а не вводить свой глобальный frame-step. Это уменьшает работу и совпадает с
семантикой игры, но делает clamp-with-discarded-overshoot особенно дорогим на
длинных интервалах (сотни game seconds при высоком TC).

**Первый тик прохождения waypoint (офлайн).**
`Dev/CurrentAtlasPrototype/strategic_waypoint_qa.py` проецирует
закрытое решение `CurrentTrack2D` на нормаль плоскости и ищет первый
100-нс тик за плоскостью (строгое неравенство `EntityRoute.Update`).
Проверяется и случай, когда группа пересекла плоскость, развернулась
под воздействием среды и к концу окна снова оказалась перед ней:
одна проверка конечной позиции пропустила бы событие. **407 PASS**,
из них 400 сверок с полным перебором тиков малых окон.
Это свидетельство для одной известной плоскости и постоянной среды,
не полный поиск игровых событий и не барьер в кампании.

**Точка изменения размера skip-чанка, не часы задним числом.** В
установленной DLL `SimulateTicks` значение `num` лежит в первом локале;
первый `ticksBeingSimulated` получает его до изменения `ticks` и
`storyTicks`. Это место, где можно передать уменьшенный интервал
всем следующим потребителям, сохранив нативное вычитание уже
пройденного времени. Тестовый probe в `CurrentClockLiveFixture.cs`
умеет ограничить его одной заранее известной датой. Обычный `Update`
меняет несколько связанных часов; доказательство для skip не
разрешает менять там только `storyTicks`.

## 11. Бюджеты и арифметика стратегической работы

Долг за реальный кадр и за игровое время:

```text
updates_per_real_second = N * (TC / H)      # группа раз в H game seconds
updates_per_frame        = N * TC / (H * FPS)
```

Иллюстративно N=8192, H=60 game seconds, 60 FPS:

- TC1: 136.53 updates/real s;
- TC140: 19,114.67/real s;
- TC10000: 1,365,333.33/real s ≈ 22,755.56/frame.

Это **не** реальное число групп и не timing. Ограниченный hot `Sample` не
спасает от неограниченного количества подшагов. Нужны общие scheduler epochs +
правильные partial intervals либо bounded timestamp cache; нельзя менять
chronology ради batching. Формула предполагает обновление раз в H=60 game s;
  в частном примере §10.1 live cadence при TC=10000 реже (~667 с на группу),
  поэтому 22,755/frame — иллюстрация спроса, не верхняя граница и не прогноз.

Предлагаемый max unprocessed lag (PROPOSED): observed/encounter-группы ≤60 game s;
unobserved ≤1 game h либо до arrival/event, что раньше. Lag журналируется, а не
маскируется. Это не измерение игры.

### 11.1 Кадровая приёмка и бюджет подсистемы

**Стартовый профиль с preload:** перед F8 зафиксировать в F0 целевой CPU/GPU,
RAM/SSD, релиз игры, драйвер, разрешение/пресет, сейвы, камеры и скрипт действий
для открытого моря, плотного конвоя и порта. Снимать интервалы между
представленными кадрами без VSync/лимитера и без Deep Profile. По три пары A/B
для каждого сценария при одинаковой настройке, после 30 с прогрева — по 120 с
непрерывного геймплея. Не вырезать провалы из окна. В **каждом** прогоне с модом:
кадры/время ≥60 FPS, p99 интервала ≤16.667 мс и p99.9 ≤25 мс. Последние два —
заданный допуск на хвосты, не измерение. Если baseline не проходит, сценарий
на этой конфигурации не принят; малая добавка мода не заменяет абсолютный порог.
Время **загрузки preload** измерять отдельно. **Длинный доковый пропуск и
пакет одновременных переходов** — обязательные стресс-сценарии F8, не просто
телеметрия. F0 фиксирует доковый старт в 12:00 при достаточном остатке
(исходник: 47 ч + 10 ticks), размер пакета и TC. На сценарий те же три
пары, прогрев и 120 с непрерывного окна; действие стартует внутри окна,
обработка и восстановление завершаются до его конца, иначе прогон не прошёл.
Снимать интервалы и во время пропуска, включая кадры, пересекающие его
границы. Те же FPS/p99/p99.9 плюс **max ≤50 мс** в каждом окне A и B:
это проектный верхний предел единичной паузы, не измерение.

Долг измерять в игровых секундах: разница между уже опубликованной эпохой
симуляции и последней подтверждённой эпохой группы. При каждом продвижении
опубликованного времени: ≤60 игровых с для наблюдаемых/encounter-групп,
≤3600 с для остальных, и ни один потребитель не видит эпоху за обязательным
необработанным событием. До публикации завершения пропуска или пакета —
**нулевой долг** для затронутых переходов и всех зависимых событий к его
целевой эпохе. Отдельно записывать ещё не опубликованный остаток запрошенного
пропуска и время его обработки: разбиение на чанки не считается выполнением
запроса. При превышении — отказ F8; ограничить поддерживаемый TC/объём,
не пропускать работу и не вырезать паузу из замера.

Стриминг и snapshots — отдельный необязательный профиль: те же
кадровые пороги, плюс холодный кеш, пересечение плиток и публикация под нагрузкой.
Их стресс не входит в окно штатной приёмки preload, а пройденный preload не
принимает автоматически необязательный профиль.

16.667 мс при 60 fps — это **весь кадр**, не разрешённый бюджет мода. Из двух
прогонов производная стоимость snapshot-запроса: 0.0846 µs (v3) / 0.076 µs (v4)
на Ryzen 7950X. При **assumed** замедлении 2.5x и 4x это даёт примерно
1,478–2,631 запросов на 0.5 мс и 2,956–5,263 на 1.0 мс. Замедления — допущение,
не измерение target hardware.

Предлагаемые пределы:

- выборка поля и диспетчер: **≤0.5 мс/кадр** main thread;
- жёсткий cap **2,048 field queries/frame** и **≤256 distinct timestamps/frame**;
- publish/refresh **никогда внутри physics step**;
- для необязательного стриминга не более одной публикации готовой плитки
  за кадр; decode вне main thread, работа публикации учитывается в бюджете;
- ни один mod-attributable кадр **>2 мс** в steady state; P99.9 tail journal;
- refresh/decode p95 5.14–7.71 / 5.99–15.11 мс из синтетики уже превышают
  удобную долю кадра, поэтому без этого расписания профиль не принимается.

### 11.2 Живой замер кадров (2026-11-21): короткие диагностические окна

Загруженная кампания на **Ryzen 9 7950X**, Windows, Unity/Mono; 48.259° N,
15.742° W, 1941-11-05. Пробник ждал ≥20 с готовности, затем 5 с прогрева
и 30 с устоя (≈55 с), после чего снимал
**15 с покоя, 15 с базовой и 10 с учетверённой синтетической нагрузки**.
VSync и `targetFrameRate` снимались только на окно и восстанавливались;
игра не сохранялась. Нагрузка — 64/256 водных запросов (34 гармоники) и
264/1056 сил ветра, **без атласа, памяти и реальных объектов**.

| Сцена | Покой: FPS / p99 / p99.9 / max, мс | ×4: p99 / p99.9 / max | >25 мс |
|---|---:|---:|---:|
| 3D TPP | 191.2 / 8.14 / 10.84 / 18.90 | 6.75 / 7.57 / 8.18 | 0 |
| Карта после правки | 209.7 / 5.90 / 20.97 / 28.07 | 6.70 / 21.62 / 23.23 | 1 (старт) |

Показанные окна укладываются в численные пороги §11.1; это не три пары F8.
В повторе TPP (`radionav-wind-probe-20261121T085401Z.json`, локальный отчёт)
покой дал **47.9 FPS**, p99 **31.92 мс**, p99.9 **54.67 мс**; причина
разницы не установлена. Самозамер синтетики **0.0056 мс/кадр** (×4 — 0.0218)
не измеряет добавку реальной функции. Это диагностика без течений и ветра.

**Причина прежних 1 Гц-хитчей найдена.** Это `LighthouseMapMarker`:
210 статических маркеров при **открытой карте** сверялись со сценой каждую
секунду; `FindObjectsOfType` + reconcile давали ~114 KB и 25–32 мс.
После отключения маркера хитчи исчезли (p99.9 21.7 мс, 0 кадров >25).
Для статического флота интервал reconcile увеличен с 1 до **10 с**
(остальные маркеры, включая свежий FIX, сохраняют 1 с). Карта после
правки проходит порог. Квитанции содержат `cameraMode`; новый `map-mode-receipt.json` также
`cameraModeEnd`/`cameraModeStable` (`Map`/`Map`/`true`), а более ранний
`tpp-mode-receipt.json` — `cameraMode: TPP`. Новые прогоны пишут все три
поля; `cameraModeStable` сравнивает только режимы на границах окна.
Ранние map-прогоны без поля давали 1 Гц-хитчи; 3D-прогон после правки —
0 кадров >25, у карты один стартовый кадр 28 мс, периодических нет.

Счётчики `GC.CollectionCount` на Unity/Mono (Boehm) недостоверны; прежний
вывод «GC 0/0/0, значит не GC» отозван. Покадровая память на старых
хитчах росла, а не падала; после устранения reconcile хитчи ушли.
Модовый поиск звёздного купола также переведён с 1 Гц на событие сцены.

**Канонический ветер:** зеркало сценического порядка дало **0°** ошибки
угла, **1.29 µs** и **0 B** на вызов (WIND §5.2). `GetWeatherDataAt`
остаётся справочным прогнозом и не используется как сила из-за другого
угла.

**Бюджетный вывод.** Живая синтетика — **0.0056 мс/кадр**; зеркало ветра
— **0.34 мс** при всех 264 уникальных точках, меньше при кеше. Полный
`GetWeatherDataAt` на 264 объекта — **≈0.9 мс + ≈25 KB/кадр**, поэтому не
горячий путь. Офлайн-выборка атласа — **0.076–0.085 µs/запрос**, K34
direct — **0.46 µs/запрос**. Из этих чисел нельзя вывести свободный кадровый
бюджет. Реальная память атласа, интеграция сил и среднее железо ещё не
измерены; F8 функции остаётся открытым.

Ограничения: одна машина (не «средняя»), один сейв и район, нет реального
атласа/ветрового поля и трёх пар A/B функции. Это baseline-замер, не
приёмка F8.

Стресс для целевой машины: **64 пробы около игрока, 200 стратегических групп,
8 разных игровых меток времени**. Для необязательного профиля отдельно
добавить публикацию и подготовку нового среза. Записывать queries/frame и
queries per simulated hour. До этого workload **не существовало**: 0.62–0.69 мс
snapshot — это batch 8192, а не frame-budget claim.

## 13. Допустимые и запрещённые упрощения

Порядок экономии:

1. убрать дублирование астрономии, allocations/IO в hot path и повторную
   геоконверсию;
2. coarse resident field + детальные регионы по покрытию, без решения океана
   в игре;
3. kinematic far-world integrator и analytic time basis; не full Rigidbody всем;
4. uniform current per hull как явно заявленное начальное приближение; без
   обещания shear physics;
5. сокращение разрешения/глубин/constituents только после измерения ошибок.
   K=8 быстрее K34, но это не доказательство достаточности восьми настоящих волн;
6. seasonal, а не day-specific modern reconstruction, с документированным
   отсутствием конкретных исторических вихрей; не заменять их шумом;
7. GPU/Burst/DOTS/SQL — не стартовая зависимость. Для десятков/сотен объектов
   CPU массивы проще и без GPU readback; это архитектурный выбор, не
   сравнительный GPU benchmark.

**Не упрощать:** exactly-once intervals, masks/units, scene-global conversion,
save/campaign lifetime, waypoint arrival и классификацию объектов. Они защищают
целостность, а не научную детализацию.

## 14. Что запрещено обещать

- 60 FPS до Unity/Mono A/B на средней машине с baseline/feature и кадровыми
  tails; offline p99 — не игровой p99.
- Что синтетический K34 является 34 астрономическими constituents или
  предиктором приливов.
- Что Deflate-коэффициент из синтетики переносится на реальный океан.
- Что `Sample` без аллокаций доказывает отсутствие GC в Unity/фоновых потоках.
- Что прототип event-locator решает общий coastal/multi-harmonic случай.
- Что точная первообразная решает движущуюся позицию/маршрут/события без
  подшагов.
- Что прочитанный порядок `SimulateTicks` уже воспроизведён в игре или что
  `TicksSimulated` покрывает обычный travel skip.
- Что таблица 8192 групп/TC — реальные данные кампании.

## 16. Остаточные пробелы

- Нет Unity/Mono A/B, реального профиля игры, кадровых tails, all-thread GC и
  пиковой памяти на средней машине.
- Нет реального NetCDF/масок/геометрии, диска, фонового loader и публикации.
- **Decode в прототипе всё ещё выделяет float reference arrays**
  (`Tile.Base`/`Tile.Coeff`): K34 — 574,600 + 67,600 float ≈ **2.57 MB на
  плитку**, выше LOH threshold; 16 плиток ≈ **41 MB transient LOH**. Это
  prototype-only и прямо противоречит использованию такой формы loader на main
  thread.
- **CoreCLR DeflateStream.Fastest даёт output больше raw** (1,288,657 →
  1,358,071 B, +5.4%) и в v3, и в v4, а Framework — меньше (1,117,439 B).
  «Сжатая» плитка может расширяться; writer обязан выбирать per-block raw, когда
  сжатие не помогает, а runtime — принимать оба варианта.
- Refresh p95 5.14–7.71 мс и decode p95 5.99–15.11 мс — большие доли кадра
  16.67 мс. Расписание и stall ceiling в §11.1 — **предложение**, не измеренная
  реализация.
- Нет repeat-run dispersion (min/median/spread over N независимых прогонов).
  V3 и v4 — не повторный замер одного кода: v4 добавляет `WorkloadPreflight`,
  поэтому разница содержит code change. p99 одного прогона нестабилен; числа
  индикативны.
- Не существовало queries-per-frame workload: 0.62–0.69 мс — batch 8192, не
  frame-budget claim. Workload из §11.1 ещё не прогнан.
- Нет общего event-locator для 2D/coastal/multi-harmonic случая и нет
  воспроизведения `Physics2D.Simulate` с chunk-sized dt.
- Прочитанный порядок игры не проверен live; открытые вопросы §10.3 остаются.
- Нет исторического предиктора 1939–1945 и юридической проверки выбранного
  пакета данных; лицензия CNES pinned commit — BSD 3-Clause, AVISO всё ещё
  цитирует GPL для prediction code; это разные версии/условия, не общий вывод.
- `artifacts/` gitignored: evidence не разрешается на чистом clone.

До закрытия этих пробелов статус: **реализация не начата, 60 FPS не доказаны,
все OC-001…OC-052 открыты.**
