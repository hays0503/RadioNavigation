# Sternspreizglas — Phase 1b: диагностика «перерисовка без подлога» (BLOCKED)

## Статус и границы

Реализация mode 4 завершена 2026-09-27/28 по этому дизайну (офлайн-гейты ниже),
живая приёмка 2026-09-28 дала **BLOCKED**: супрессия scope работает, колбэк
пишет `drawIssued=true` без ошибок, но перерисовка не кладёт ни одного пикселя
тремя материалами — меш не растеризуется в кадровом пути (доказательства
ниже; вероятно, и нативно тоже — см. F-находку). Контракт mode 3
(pass-through) не меняется и по-прежнему защищён SourceCheck.
`RadioNav.SternspreizProbe` по умолчанию остаётся OFF. Без живой перерисовки
mode 4 production-решением не является.

## Зачем нужен этот гейт

Phase 1a доказывает подавление модового `StarSkyRoot` в каждом PIP при
нетронутом Main, но явно **не** доказывает, что результирующий кадр можно
перерисовать без необработанного подложного слоя. Этот гейт закрывает ровно
этот разрыв: после того же подавления колбэк PIP сам кладёт диагностический
звёздный слой. Прохождение доказывает установку пикселей без модового
подлога — и ничего про оптику PSF, исключение Sun или production-архитектуру.

## Узкий дизайн (для будущей реализации, не для этой фазы)

- Новый явный opt-in режим mode 4 (`RadioNav.SternspreizProbe = 4`). Mode 3
  остаётся pass-through: его SourceCheck-контракт запрещает отрисовку,
  поэтому mode 3 **не** расширять — добавлять режим.
- Та же цель/регистрация/восстановление, что в mode 3: существующий
  `MeshRenderer` объекта `StarSkyRoot`, только обе PIP-камеры, финализатор
  Harmony восстанавливает renderer, OFF/закрытие/уничтожение снимают
  регистрацию. Изменений render-scope нет.
- Колбэк: требовать то же доказательство супрессии в текущем кадре
  (`IsSourceSuppressedForCurrentRender`), затем Blit source→destination (как
  сейчас) плюс ОДИН `DrawMesh` уже существующего
  `starsMeshFilter.sharedMesh` диагностическим тонированным материалом на
  аддитивном `Sprites/Default` пути (та же шейдерная семья, что нативный
  звёздный слой; новых шейдеров нет, вырезанный `Unlit/Color` запрещён).
  Урок 2026-09-28: `Hidden/Internal-Colored` с нормальным блендом оставляет
  субпиксельные low-alpha квады ниже джиттера рендера — первая mode-4 попытка
  была невидима при `drawIssued=true`; One/One-накопление воспроизводит
  нативную видимость в зелёном).
- Матрица отрисовки — единичная (вершины меша в мировых координатах, как их
  строит `StarsMesh`) — подтвердить на момент реализации; если неверно,
  сначала исправить этот дизайн, потом писать код.
- Тонировка плоская, не белая — чтобы перерисованный слой отличался и от
  родных звёзд неба, И от неподавленного белого модового подлога.
- Запрещено, перенесено из Phase 1/1a: любое использование
  `SternspreizPsfMath` (остаётся офлайн), клонирование/перестройка меша
  (`RebuildMesh` остаётся запрещён в probe), GameObject-ы на звезду,
  глобальный blur/порог, любой выбор Sun/Moon/планет/созвездий (`TOD_`,
  `SunDisc`, `MoonDisc`, `PlanetRenderer`, `ConstellationMesh` остаются
  запрещены в probe + scope), записи в Main Camera.

## Реализация (2026-09-27/28, офлайн)

- `Source/UI/SternspreizPipProbeEffect.cs`: константа `StarRedrawMode = 4`,
  `CurrentMode` принимает 4, супрессия требуется и в mode 4, `ExecuteProbeDraw`
  в mode 4 вызывает новый `DrawStarsMesh` (один `DrawMesh` существующего
  `sharedMesh` с единичной матрицей и chartreuse-материалом); mode 3 из
  `ExecuteProbeDraw` по-прежнему отсутствует. Материал уничтожается в
  `Dispose`; форма снапшота/лога не менялась.
- Фикс материала 2026-09-28: первая попытка (Internal-Colored, обычный бленд)
  вживую дала `drawIssued=true` при нулевых видимых пикселях — субпиксельные
  low-alpha квады тонут ниже джиттера. Материал переведён на
  `Sprites/Default` + `_ZWrite 0` с явной белой 1×1 текстурой (несвязанный
  сэмплер читает чёрный, чёрный аддитивно даёт ноль — вторая попытка показала
  ноль депозитов даже с текстурой). Финальный бленд One/One LOUD: игнор малой
  vertex alpha, полный тинт на покрытый пиксель — фотометрия сломана
  намеренно, тестируется установка. Fallback на Internal-Colored, если
  спрайтный шейдер недоступен.
- `Source/UI/SextantPipFactory.cs`: mode 4 прячет фикстуру и регистрирует тот
  же `StarSkyRoot`-renderer на оба PIP; OFF/close/teardown без изменений.
- `Source/Logic/SternspreizPipRenderScopePatch.cs`: scope подавляет
  зарегистрированный renderer и в mode 4; восстановление финализатором без
  изменений. Изменений render-scope механики нет.
- `SternspreizPsfMath` не затронут и не ссылается из runtime (гейт ниже).

## F-находка: звёздный меш мода, возможно, не растеризуется нигде

Всё активное содержимое PIP-кадров (белые звёзды) может быть родным TOD-куполом,
а модовый `StarSkyRoot` — невидимым во всех камерах с момента введения
(P4-адаптация переписывает alpha; идентификация тел при этом работает —
она математическая, не растровая). Проверено и исключено: матрица (identity +
сдвиг), материал (3 варианта), цель/буфер (контроль виден), супрессия scope
(телеметрия), границы/индексы/цвета меша (конечны), far-plane (3825 < 4500),
слои (Default везде), NaN (нет), winding (доказан корректным, см. ниже),
глубина (проходит даже при 16 бит), расхождение счётчиков (дрейф перестроек).
Остаток: GPU-upload аномалия вершинного потока, Cull-состояния встроенных
шейдеров (из доступных доказательств неизвестны), доказательство видимости
натива в Main. Живые чтения состояния объекта выполнены (всё живо).
RenderDoc-захват заблокирован отсутствием инструмента: `renderdoccmd` нет в
PATH, `C:\Program Files\RenderDoc` отсутствует, в `captures/` только
`uboat.mp4` (проверено 2026-09-28) — для захвата нужны установка RenderDoc и
шаблон захвата от пользователя.

### Разбор winding и глубины (2026-09-28, офлайн; игры в процессах не было)

Winding квадов `BillboardQuadBuilder.AddQuad` вычислен точно вручную: при
взгляде со стороны камеры треугольник (v0,v1,v2) идёт низ-право → низ-лево →
верх-лево, т.е. по часовой. По Unity Manual («Mesh data / Winding order»:
front face — clockwise) это лицевая сторона к камере. Winding реабилитирован
строгой математикой (черновое «CCW» было арифметической ошибкой автора);
двусторонность сентинела — просто перестраховка, не улика.

Глубина тоже проходит численно: звёзды на 3825 м при far 4500 дают NDC-глубину,
отличимую от очистки даже при 16-битном буфере (а при равенстве LEqual всё
равно пропускает). Облака при этом корректно перекрывают — это ожидаемо, не
аргумент против.

Расхождение счётчиков (verts 420 против colors 416 в разных чтениях) — не баг
потоков, а дрейф перестроек за ночь (лог: 104→105→106 звёзд); чтения взяты в
разные кадры.
