## Build system

Raw `csc.exe` via PowerShell — **not** `dotnet build`/MSBuild SDK. Needs local UBOAT install for Unity/game DLL refs.

```powershell
powershell -File build.ps1 [-GamePath <path>] [-Configuration Debug|Release] [-OutputDir .]
```

Default game path: `C:\Program Files (x86)\Steam\steamapps\common\UBOAT`. Output: `radionavigation.dll` in project root.

**PVS-Studio gate (always runs, blocking):** after a successful csc compile, `build.ps1` invokes `pvs.ps1`, which analyzes `RadioNavigation.Analysis.csproj` (net48 + real game DLLs) with `PVS-Studio_Cmd.exe` and converts the report to `pvs-report.txt`. A non-zero PVS result fails the build. Run standalone via `powershell -File pvs.ps1 [-Configuration Debug|Release] [-Json] [-Sarif]`. Suppressions live in `RadioNavigation.pvsconfig` (referenced by Analysis.csproj) — disabled codes are Unity/extension-guard false positives documented there; do NOT re-add inline `//-V:` comments (C++-only, ignored for C#). Keep PVS clean before committing.

**Important:** game **recompiles mod from `Source\*.cs`** at load (Roslyn, `Mod.cs Compile()`) — build.ps1 DLL unused at runtime. Game compile defines: `UBOAT`, `UBOAT_2024_1`, `UNITY_STANDALONE_WIN` — **no `DEBUG`**, so `#if DEBUG` blocks stripped at runtime regardless of build.ps1 config. Local builds = IDE/static checks only.

**C# language version = 7.0 (game RoslynCSharp contract, verified in-game 2026-09-03):** the game compiler rejects anything newer (e.g. `default;` literal = C# 7.1 → CS8107) and then loads a broken assembly (`BadImageFormatException`). Mod sources must stay C# 7.0. Enforced statically in three places: (1) `build.ps1` Roslyn branch passes `/langversion:7`; (2) `ModCompiler.GameParityParseOptions` (C#7 + game defines, no DEBUG) pins every mod-source parse in SourceCheck, so `Mod_CompilesAgainstCleanGameApi` fails offline on any newer-feature use; (3) the same test also fails on CS0169 (never-used field — dead code after extractions). CS0649 (never-assigned `[Inject]` fields) is the DI pattern, allowed. Consequence: never use `const bool` as a feature gate — const folds away and produces CS0162 unreachable-code in the game compiler; use `static readonly bool`.

## Neural-slop guard (RadioNavigation.SourceCheck)

Compiles the mod's `Source\**\*.cs` against a **clean, non-obfuscated signature-only reference** built from the real game source (`C:\code\projects\uboat`), so a hallucinated/wrong-signature game API call fails the build instead of passing silently against the obfuscated DLL. Run: `dotnet run --project RadioNavigation.SourceCheck -c Release` → 56 tests, all PASS.

- **`GameSource_CompilesClean`**: the dependency-closure subset of the decompiled game source (only files the mod's game-API surface touches) must compile cleanly with bodies stripped. If this fails, the clean reference is unavailable and the guard can't run.
- **`Mod_CompilesAgainstCleanGameApi`**: compiles the mod against the emitted clean reference + real Unity/third-party DLLs. Any CS Error = the mod calls a game API that doesn't exist / has the wrong signature → neural slop → FAIL. Cached at `obj/cleanref/com.uboat.game.clean.dll` (`CleanReferenceCache`), invalidated by game-source/DLL/mod-source content hash.
- **Gate in `analyze.ps1`**: SourceCheck runs as a **blocking gate** before Roslynator analysis (skip with `-SkipSourceCheck`). A FAIL stops the analysis with exit 1. **Performance (measured 2026-09-26)**: first run after an input change ~294 s (full seed comparison), then ~16 s — `SeedQuality_NewVsOld`/`DllOnlyTypesAreBounded` skip via per-test stamps (`seedquality-<test>.stamp` next to the clean-ref cache) when game sources, Managed DLLs, mod sources and this tool's own sources are unchanged; the stamp is written only on PASS, so a failure always re-verifies. `analyze.ps1` prints the SourceCheck/Restore/Roslynator split via `Write-PhaseTimings` before every terminal exit.
- **`Probe_MissingTypes`**: reports which referenced types resolve to which Managed DLL (sanity probe).
- **Cyclomatic-complexity gate** (2026-09-02): `MethodComplexity_NoSuperMethods` computes cyclomatic complexity over the mod's own `Source\**\*.cs` (1 + if/else-if, switch case, for/foreach/while/do, `?:`, `&&`/`||`/`??`, conditional-access, catch; nested lambdas/local functions counted as separate methods). Threshold **15**, FAIL on exceed → super-method refactor candidate. All 14 methods that exceeded 15 were refactored into sub-methods (2026-09-02) — gate now PASSes.
- **Seed discovery** (`DependencyClosure.ComputeSeedTypes`): two passes — (1) syntax pass for any simple type name the mod uses that exists in the game source (catches obfuscation-renamed types like `Periscope`); (2) **member-chain expansion** — resolves mod member-access chains (`gameMainCamera.GenericController.ExternalController`) against the game-source member index, iterating to a fixed point, so types reachable only as property return types (e.g. `GenericCameraController` via `MainCamera.GenericController`) become seeds too. (A semantic pass against the obfuscated DLL was removed 2026-09-02 — it was redundant: every type it found also exists in the game source, and it cost ~205s.)
- **Quality regression tests** (2026-09-02): `SeedQuality_NewVsOld` re-runs the old semantic+ syntax+member-chain algorithm and asserts the seed set (names + arity) is identical to the new one — 0 diffs. `SeedQuality_DllOnlyTypesAreBounded` asserts **0** types in `com.uboat.game.dll` are missing from the game source, so the syntax pass cannot miss any DLL type (the "type in DLL but not source" hole is empty). Both PASS.
- **Reference DLLs** (`ModCompiler.ModRefNames`): clean game assembly + BCL (net40 mscorlib/System) + `0Harmony`, `com.uboat.modapi` (InjectAttribute/ISingleton), `com.uboat.rendering` (AdditionalCameraData), `com.uboat.dependencies` (TOD_Sky/LipSync/Blake2), TextMeshPro, postprocessing, water, UnityEngine modules. `com.uboat.game.dll` is deliberately EXCLUDED (that's the obfuscated one the whole guard replaces).
- **Stub machinery** (`DependencyClosure`): non-seed referenced types are stubbed as empty classes/enums/interfaces in the correct namespace, with generic arity, nested types, enum members, and member-property stubs (`<M:T,...>`) resolved from the full-source member index. Broken `using` namespaces stripped only for `UBOAT./DWS.` (never `UnityEngine.`). Diagnostic messages are Russian with double quotes — parsers handle both quote styles.

Мера: p99 радиального `|ΔL|` в кольце r 300…352 упал **33.7 → 22.1**. Инвариант закреплён тестом `NoRadialBandEndsInASinglePixelStep` (светлота ребра ≤ `MaxLuminanceRisePerPixel = 0.075`/px, три направления света; мутация `0.002` → 0.162 FAIL) — считать надо **композитную светлоту**, а не alpha: трубка уже ~95% непрозрачна у фаски, поэтому ступенька видна в цвете, а не в покрытии. **Луна в окуляре — вход от скорости камеры (2026-10-02)**: автор потребовал «курсор включён, камера не может двигаться, а значит и окуляр не может двигаться, и луны быть не может» → входом стала **угловая скорость взгляда**, а не оси мыши (у мыши нет состояния «камера заблокирована», и фильтр вниз по потоку это не чинит). Чистая `Source/Logic/SextantAimRate.cs`: обе оси через `BodyRowFormatter.Wrap180` (euler заворачивается 360 → 0), **отбраковка прыжка по скорости** 900 °/с с переустановкой латушки на любом отброшенном кадре, `dt` вне `[1e-4, 0.25]` → переустановка без деления, NaN-поза не латушится, 15 тестов по одному на риск. Скорость меряется **до** стабилизации вымыванием (`SextantPipPose`, `targetYaw = mainEuler.y + yawTrimDeg`), латушка сбрасывается в `ResetFilters`; алитады в `targetYaw` нет by construction. Отклик `max·√(min(1,|ω|/ω_full))`, мёртвая зона 0.35 °/с, `ω_full` 70 °/с, **ход 0.34 → 0.15** (при 0.34 ближняя граница тени на `0.985 − 0.34` = треть радиуса — читается как чёрный укус, а не как серп). Первая версия `Axis` начиналась с `if (rate <= 0) return 0` и **молча убивала половину поля** — поймал тест `CrescentFormsOnTheOppositeSide` (3 из 4 теорий). - **Светлая дуга снаружи апертуры (2026-10-02)** — виновник найден по конструкции, **не по замеру**: `LensBacking` единственный элемент без маски (`maskable = false`), вне апертуры у него `alpha = 0`, а шейдер писал `color.rgb * (1.0 - shade) + rim` **без покрытия**; канва, composites premultiplied, добавляет RGB независимо от alpha. Фикс: `color.rgb = (color.rgb * (1.0 - shade) + rim) * coverage;` — накрывает и сам член тени (на ближней к зрачку стороне поле за кромкой затемнено не полностью). `fwidth(shadeDistance)` теперь ограничен `clamp(…, 1e-5, 0.05)` (производная `length()` меняет знак в центре), а зависимость `rim` от яркости сцены переехала на гладкую рампу — см. следующий пункт. **Первая гипотеза (`Glare`) отозвана**: вуаль была убрана в 0.97 от окуляра и откачена, потому что замер её не подтвердил; сейчас `GlareScale = 1.0` с комментарием, фиксирующим проверку, и гейтом «размер обязан быть именованной константой».
- **Рваные дуги у кромки при сильном движении мыши (2026-10-02)** — автор прислал кадры и обвёл участок **правой** кромки. Диагноз сделан **по геометрии**: полоса `rim` лежит на окружности `|p − c| = R`; в покое `c = 0` и она тонким ровным кольцом на r = 0.985 (вариант «д»), а при ходе 0.15 на стороне зрачка уходит **с кромки в поле** (r ≈ 0.885…0.996) — отмеченный прямоугольник это ровно r 0.93…1.0. Другого яркого узкого члена там нет: `EdgeRing` и наглазник статичны, `Glare` при Солнце под горизонтом равен нулю, звёзды — отдельные точки. Вторая, более важная причина — **жёсткий порог** `saturate(color.r * 4.0)` при яркости 0.25: на текстуре облаков сцена пересекает порог пятнами, и стена трубки появляется только выше него, то есть полоса рассыпается на обрывки. Фикс: `SextantLuneMath.WallResponse(luma) = 0.2 + 0.8·min(1, luma/0.5)`, в шейдере зеркально `0.2 + 0.8 * saturate(sceneLuma * 2.0)`; пол держит тёмное море тёмным (0.2 × 0.09 = 0.018), потолок ровно 1. **Сила 0.09 не менялась** — яркость автор не просил, а менять её вслепую значит менять вид по гипотезе (ровно то, что было отозвано с `Glare`). Крутилка **`RadioNav.LuneRim`** (тысячные, потолок 0.5 как в `Range` шейдера) обязательна потому, что рантайм-материал не адресуется по имени через reflect, а без неё у автора нет способа A/B-ить единственный член, который может читаться как дефект; A/B занимает 5 секунд и делается без пересборки. Инвариант теста — **не «тусклее», а «нет шва»**: непрерывность, монотонность, крутой шаг < 0.01 на 1/4000 диапазона, пол и потолок, `NaN`/`±∞` → чёрная сцена (иначе NaN уехал бы в материал и погасил всё поле). Гейт запрещает `saturate(color.r * 4.0)` **по имени** — иначе «упрощение» вернёт излом и будет выглядеть как правка кода, а не как регресс. **Ловушка методики:** когда связь недоступна, правильный ход — идентифицировать член по геометрии артефакта (его радиус вычисляется из формулы), а не объявлять правку; здесь pixels-приёмки нет (iGPU, чёрный композит) и граница приёмки записана явно. Разбор крутилки вынесен в чистый контракт `SextantLuneMath.RimLightFrom(int тысячных)`: пока оверлей зажимал сам (`Math.Min(RimLightMax, …)`), две мутации выжили все гейты — потолок × 0 (стена не светится никогда) и зажим на 1 вместо 0 (A/B автора невозможен).

Pure-математика (например `WallResponse`) для него невидима — SourceCheck сверяет мод с API игры и с текстом исходников, а не с поведением чистой функции; три из пяти мутаций «выжили» именно поэтому, пока харнесс гонял один гейт. Гейт `SextantPip_AimProbeIsWiredInertAndSelfStopping` (8 правил A–H) проверен **9/9 мутациями**; **две дыры нашлись при мутациях, а не при чтении**: (а) проверка `InvokesName(update, "Advance")` цеплялась за **чужой** вызов `SextantAimRate.Advance` в том же методе — теперь `InvokesOnType(..., "SextantAimProbe", "Advance")`, проверка вызова с указанием типа; (б) «есть ли где-то нулевой дефолт» пропускало мутацию, где ненулевой дефолт стоял у **одной** из двух крутилок — теперь требование по каждому ключу. Общий урок уже знакомый по гейту луны: **проверять вызов, а не имя**, и **не собирать условие «хоть где-то»**, когда требование относится к каждому элементу. **Третья дыра того же рода:** мутация «`IsFreshRun` всегда true» SourceCheck **не видит вообще** (гейт структурный и видит только вызов), её поймали **тесты** — 3 падения. Мутация засчитана пойманной, если упал **любой** гейт, поэтому чистая функция обязана иметь своего владельца среди тестов, иначе её семантика не защищена ничем.
- **ЛУНА: стенка едет вместе со зрачком — это и есть «неправильное отображение при резких поворотах» (2026-10-02, исправлено)**. В шейдере **и тень, и подсвеченная стенка** считались от одного поля `shadeDistance = length(p - _LuneOffset) - _LuneRadius`. Но стенка принадлежит **трубке**, а трубка неподвижна: зрачок лишь открывает и закрывает её. Из-за общего поля стенка уезжала вместе со зрачком — на резком повороте до `_LuneRadius − MaxOffsetUnits` = **0.835 радиуса**, то есть **в середину поля**, и по нему бежала светлая дуга. Это ровно то, что описано в комментарии самого шейдера («автор видел рваные светлые дуги у кромки при сильном движении мыши, r 0.89–1.0, после того как смещение зрачка оттянуло стенку от кромки в поле») — **механизм был назван тогда и не исправлен**: правили яркость (`wallResponse`), а геометрию оставили ездящей. Правка в двух слоях: (1) **корень, шейдер** — `float wallDistance = length(p) - _LuneRadius;` стенка стоит на своей оси, тень её открывает; (2) **выразимое в C#, `SextantLuneMath.WallLight(rimLight, offset, maxTravel)`** — яркость стенки падает пропорционально уходу зрачка, в покое полная (ровно тот «вариант д», который выбрал автор), к полному ходу ноль. Обе копии шейдера синхронизированы побайтно. **Пиксельная приёмка оффлайн** (симуляция арифметики шейдера, яркость стенки зафиксирована на 0.09, чтобы C#-половина не маскировала геометрию) — **насколько глубоко в поле заходит стенка**: покой **0.978 → 0.978** (неразличимо, выбранный вид сохранён), половина хода **0.903 → 0.978**, полный ход **0.828 → 0.978**. То есть по старому коду стенка на резком повороте ныряет на **15 % радиуса в саму картинку** и бежит по ней; по новому стоит на трубке. **Методическая ловушка, найденная при этой приёмке:** первая полоса измерения была 0.80–0.87, и разница показалась нулевой — дуга OLD касается r ≈ 0.83 **в одной точке** окружности, это меньше 1 % пикселей кольца, и p99 её не видел; правильный вопрос не «сколько света в полосе», а **«насколько глубоко стенка заходит»**. Ещё две ошибки того же прибора: подставлена уже погашенная C#-яркость (маскировала эффект шейдера), и яркость `wallResponse` на яркой сцене = 1.0, то есть стенка **максимальна именно там, где автор её и видел** — на светлых облаках. **Проверенная гипотеза, которая НЕ подтвердилась:** «картинка внутри размывается при быстром движении, а обод нет» (пост-обработка PPv2 против UI-слоя). На видео автора `corr(движение, резкость картинки) = −0.078` — **связи нет**; разброс резкости ×3.76 объясняется **содержимым** (гладкое небо против резких облаков), а «постоянство» обода оказалось 0.0196 = ровно 5/255, то есть **порогом 8-битной квантовки**, а не структурой. Вывод: гипотезу надо уметь **опровергнуть**, иначе она не отличима от правдоподобной.
- **Дыра в гейте: вызов есть, а аргумент не тот (2026-10-02)** — гейт требовал, чтобы `SextantLuneOverlay.Write` вызывал `SextantLuneMath.WallLight`.
