# P1.Q9_TightCoupling_AudioSynthesisEngineArrays

**Приоритет:** P1-Major  
**Область:** Sound — API design / tight coupling to array topology  
**Статус:** Новый документ, не задокументировано  

---

## Описание проблемы

Сигнатуры `AudioSynthesisEngine.ProcessAudio()` и `UpdateStationBeats()` принимают **5+ raw arrays** с жёстко связанной позиционной семантикой — это антипаттерн tight coupling который делает API хрупким без обёртки или abstraction.

```csharp  
// AudioSynthesisEngine.cs строка 65: основной аудио processing метод
public void ProcessAudio(float[] data, int channels, 
    StationState[] stations,           // array #1 — station states (14 entries)  
    StationScheduler[] schedulers,     // array #2 — match by index to stations
    MorseKeyer[] keyers,               // array #3 — match by index to stations  
    CarrierGenerator[] carriers,       // array #4 — match by index to stations
    bool radioOn, int currentZoneIndex, 
    int sonneZoneIndex)

// Строка 52: helper method с тем же паттерном  
public void UpdateStationBeats(StationState[] stations, CarrierGenerator[] carriers, ...)

```

### Анализ проблемы

Каждый из этих массивов (`stations`, `schedulers`, `keyers`, `carriers`) должен иметь **identical length** (14 = число beaconов) и соответствовать по индексу элементу станция N → scheduler N → keyer N → carrier N. Если массивы mismatch по длине или индексу — код может silently produce wrong audio, crash с IndexOutOfRangeException при runtime, или silently corrupt state через invalid array access.

Это **positional coupling** (position-based dependency) вместо **named binding**. Любая из этих парадигм уязвима к:
1. Разной длине массивов которые вызваны разными consumers
2. Изменённому порядку элементов без ре-сортировки всех массивов параллельно  
3. Невозможности safely add/remove stations dynamicly

## Почему это проблема

1. **Brittle API — zero validation on array alignment.** Нет проверки что `stations.Length == schedulers.Length == keyers.Length == carriers.Length`. Если кто-то когда-нибудь передаст массивы разных длин (например из-за bug в SonneController), код может либо crash silently corrupt data. Слот `[n]` stations будет match `[n]` scheduler но не обязательно правильная станция.  

2. **Caller — SonneController must maintain manual alignment invariant.** SonneController.cs строка 48-53:
   ```csharp
   // Caller обязан аллоцировать и синхронизировать arrays вручную  
   stations = new StationState[beaconStations.Length];     
   schedulers = new StationScheduler[beaconStations.Length];      
   keyers = new MorseKeyer[beaconStations.Length];        
   carriers = new CarrierGenerator[beaconStations.length];
   ```
   Каждый future caller должен понимать этот implicit invariant и его правильно implement — potential для subtle bugs.  

3. **Нельзя безопасно добавлять/удалять stations dynamically.** Добавить beacon в середину массива означает переставить все элементы во всех 4 arrays одновременно с одинаковым alignment. Это сложно рефакторить если код растёт.

## Риски

| Риск | Вероятность | Влияние |
|------|-----------|--------|-----
| Array length mismatch between callers | Выше-средний при code changes в caller side → subtle audio bugs or random IndexOutOfRangeException crashes 
Caller manually maintains alignment invariant, error-prone | Callers must ensure array indexes map correctly
