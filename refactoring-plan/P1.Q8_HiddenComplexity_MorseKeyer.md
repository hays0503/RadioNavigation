## Описание проблемы

`MorseKeyer` из 240 строк объединяет **сложный state machine с scheduler coupling и дублированием логики**. Класс содержит ~6 private методов и сложную логику перехода между состояниями, где два разных пути данных (IKeySequence vs NavigationPattern[]) требуют дублирования condition checks.

### State Machine Complexity

```csharp
// MorseKeyer.cs: строки 7-13 — inline enum state machine
private enum State { Idle, ElementOn, ElementSilence, Tone }

// Два разных data paths с повторяющейся logic
private IKeySequence sequence;           // path #1 для letter sequences  
private NavigationPattern[] consolPattern; // path #2 для CONSOL cycles each station uses
```

### AdvanceElement() — ~50 LOC сложной ветвистой логики

Строки 142-198 содержат double-linked progression: если current consolPattern exhausted → check scheduler → get next pattern → load it OR if sequence exhausted → check scheduler → get next seq → load it. Каждый branch имеет идентичный structure: check scheduler → call OnSequenceFinished() → GetCurrentXXX → validate empty → StartElement().

```csharp
// MorseKeyer.cs строки 146-172 — CONSOL path (50 LOC)
if (consolPattern.IsNotNull() && elementIndex >= consolPattern.Length) {
    OnSequenceFinished?.Invoke();
    if (scheduler.IsNotNull()) {

        var nextPattern = scheduler.GetCurrentConsolPattern();
        if (nextPattern.IsNotNull() && nextPattern.Length.IsPositive()) {
            consolPattern = nextPattern; elementIndex = 0; callsignLength = 0; StartElement(); return;
        } else { state = State.Idle; IsActive = false; return; }
    } else { elementIndex = 0; }
}

```

### GetCurrentElementType() и GetCurrentSoundTicks() — дублирование

Строки 203-236 имеют identical condition structure: сначала проверяют `consolPattern` then `else if sequence`, each with index bounds checks. Эту логику можно extract в ~5 LOC method или helper class, но вместо этого она копирована дважды (в GetCurrentElementType AND GetCurrentSoundTicks AND GetCurrentSilenceTicks = three copies total).

## Почему это проблема

1. **Cognitive load для reviewers.** AdvanceElement() ~50 LOC double-branch logic затрудняет понимание что произойдёт когда pattern exhausted. Две копия identical structure увеличивают вероятность inconsistent changes когда код эволюционирует (если fix применяются только к CONSOL path и not sequence path).

2. **Duplicated null-check conditionals.** Каждое `if (consolPattern.IsNotNull() && ... else if sequence.IsNotNull()...)` копируется 3 раза в GetCurrentElementType, GetCurrentSoundTicks, GetCurrentSilenceTicks — это легко сломать если одна копия обновится а другая forgotten.

## Рекомендованное решение

1. **Extract unified accessor method:** создать `GetCurrentSequenceOrPattern()` который возвращает abstraction over both paths (IKeySequence-like interface) → eliminates triple copy-pasted null-check conditional logic
2. **Simplify AdvanceElement():** extract scheduler callback pattern into single helper method — current ~50 LOC можно reduce к ~15 LOC с extraction:

```csharp
// Proposed simplification structure
private void LoadNextFromScheduler<T>(T[] nextPattern, Action loadAction) where T : struct {
    if (nextPattern.IsNotNull() && nextPattern.Length > 0) { pattern = next Pattern; elementIndex = 0; loadAction (); }
    else { state = State.Idle; IsActive = false; }
}

// Then в AdvanceElement():
LoadNextFromScheduler(scheduler.GetCurrentConsolPattern(), () => StartElement());
```

3. **Или полный refactor to single abstraction:** сделать IKeySequence и NavigationPattern[] (через wrapper) реализовывать один общий интерфейс `IBeaconSequence` → morseKeyer может работать с одним типом eliminating dual-path branching entirely
