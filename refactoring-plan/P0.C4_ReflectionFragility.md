# Fragile Reflection-Based Game Integration (RadioStoryIntegration)

## Problem

The entire integration with UBOAT's story system consists of runtime type resolution — no compile-time verification for game version compatibility. If a method or event changes between patches this code silently returns early without any indication to the player that the mod failed to load correctly.

### Triple-Duplicated Code (Lines 297-306 and 314-321)

Three identical copies of exact same resolution logic pattern:
```csharp
// Copy #1 — lines 297-305
Type.GetType("DWS.Common.InjectionFramework.ScriptableObjectSingleton, com.uboat.game") 
    ?? typeof().Assembly-CSharp

// Copy #2 — lines 314-321
Type.GetType("InjectionFramework.ScriptableObjectSingleton, ...")

// Copy #3 in another method — same pattern repeated
```
A simple extract-to-method would eliminate this duplication **and** reduce fragility. The duplicated code structure makes it harder to fix any single type resolution error because all three copies are identical and hard-coded separately.

### Brittle Constructor Resolution (Line 74)

Lines found at line constructor parameter check on `param[3].ParameterType == typeof(Action)` — fragile; adding a Action-parametered constructors silently breaks this code path as well.

### Dynamic Construction (`CreateDecision()` lines 201-229)

```csharp
// Lines 201-28 - dynamically fills ctor arguments with Activator.CreateInstance or nulls
Activator.CreateInstance(paramType) ?? null
```
If required constructor parameter changes type order, silently passes mismatched data to the game. No compile-time validation of expected structure at runtime via the game's types.

### Silent Fail/Open Anti-Pattern (Lines 362-366)

```csharp
catch (Exception ex) {
    Debug.LogWarning("[RadioNav] HandleCustomDecisions failed (fail-open): " + ex);
    return AllowOriginal; // true — original story proceeds unchanged!
}
```
Any internal error in this integration silently restores game default behavior: the mod crashes silently when itself it crashes means players will have no radio interface but indication which is broken...A dedicated logging mechanism is needed.

## Recommended Fix

1. Extract all reflection-based type resolution into a new `GameApiCompatibilityChecker` class with explicit validation of method signatures & expected interfaces at startup (Main.cs OnLoaded pre-flight check).
2. Report **all** missing types, methods and/or events in one consolidated log message to the player (fail-fast fail-hard: if integration fails show user error about mod loading failed".
3. Replace triple-duplicated resolution code with single dedicated method & pass via Dependency Injection.
