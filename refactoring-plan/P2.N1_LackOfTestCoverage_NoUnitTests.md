## Описание проблемы

Проект RadioNavigation **полностью отсутствует unit test infrastructure и тестовые случаи** несмотря на 16-главный Software Architecture Document (SAD) который в главе 11 proposing target >60% code coverage — но ни один тестовый файл не существует.

### Что было запланировано по SAD

Глава 11 propose >60% покрытие为核心逻辑 с unit testing для PositionFixCalculator, MorseKeyer, AudioSynthesisEngine но **none реализован до сих пор**. Full set of 60+ test cases proposed but zero implemented:

- No `[Test]` attributes anywhere in project
- No `xunit`, `nunit`, `minitest.net` или any test framework referenced в .csproj  
- No `*.Test*` или `*_tests.cs` files exist — все *.cs файлы находятся под `Source/` только production code

### Какие модули критически нуждаются в тестах (в порядке приоритета)

| Module | LOC | Risk Level | Proposed Tests Count | Why critical |
|--------|-----|------------|---------------------|--------------|
| `PositionFixCalculator.Calculate()` | 95 | Высокая | 10+ tests | Core navigation math — errors here put ship wrong position silently |  
| `MorseKeyer.Advance()` + state transitions | ~70 | Средняя | 8-10 tests | Signal timing critical for correct CONSOL pattern generation  
| `AudioSynthesisEngine.ProcessAudio()` | ~45 | Средняя | 5-8 tests | 44kHz real-time DSP — must validate no crash/leak per frame
| `SonneController.OnUpdate()` loop logic | ~60 | Низкая | 3-5 tests | UI + audio mixing — mostly visual/timing not safety-critical  
| DialConfig.FormatFrequency() / AngleToFrequency() | ~28 | Низкая | 4-6 tests | Unit conversion must preserve kHz precision
| `ConsolCycleConfig` и beacon data lookups | ~15 | Низкая | 3-4 tests | Static config — could be integration tests 

## Риски

| Риск | Вероятность | Влияние | 
|------|-----------|--------|-----
| Silent regression on code changes — any refactor может сломать navigation math без detectable test failure because no assertions to fail. Developer only discover bugs при play-testing game manually | Высокая (постоянная) | Каждый future change is a risk — even simple extraction like Q3,Q4,Q6 could introduce subtle position or timing errors undetectable without unit tests
No automated CI pipeline для mod — build succeeds but runtime logic broken because static analysis doesn't catch math/algorithm issues.  
Adding new beacons/config changes risk misalignment with real-world navigation specs | Средняя | Wrong bearing/frequency values produce invalid fix

## Рекомендованное решение (3-phase approach)

**Phase 1: Add xUnit/minitest.net к project — setup infrastructure only**
```xml
<!-- .csproj additions -->
<PackageReference Include="minitest" Version="..." />
<ItemGroup> 
  <None Update="TestData\*.json" CopyToOutputDirectory="PreserveNewest" />  
</ItemGroup>
```

Create test project `Tests/` parallel к Source/ с базовыми assertion patterns для pure math methods.

**Phase 2: Тесты для core algorithms first (10-15 тест cases)**
```csharp
[TestClass] 
public class PositionFixCalculatorTest{    
    [TestMethod]     
    public void Calculate_TwoBeacons_ValidIntersection()
  { // Test с known coordinates → expect expected latitude/longitude within tolerance        
    }       
    
    [TestMethod]        
    public void Calculate_FewerThanTwoMeasurements_ReturnsInvalid()        
    { /* assert .Valid == false */ }  
}

[TestClass]{
[TestMethod]   public void Advance_TickIncrementsStateCorrectly()        
{ /* validate state transitions: Idle -> ElementOn -> ElementSilence -> Tone — based on MorseTiming constants */ }
} 
```

**Phase 3: Драйверы-тесты для UI + integration tests**
Создать интеграционные тесты которые mock Unity DI и check RadioHandler visibility/toggles, AudioSynthesisEngine ProcessAudio produce valid float[] output.
