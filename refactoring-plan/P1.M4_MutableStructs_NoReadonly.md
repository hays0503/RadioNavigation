# Mutable Structs — StationState, Measurement, FixResult without readonly

## Problem

Multiple critical value types are declared as mutable structs: `StationState`, `Measurement` and `FixResult`. All fields are public with no `readonly` / `init` modifiers. This creates subtle bugs when struct instances are copied by value (which happens automatically for value types in C#). When code reads a field from an array element it gets a COPY — modifying that copy doesn't write back to the original unless explicitly re-assigned:

```csharp
// Bug pattern: s is a COPY here, not a reference!
var s = GetStation();  // struct copied by-value
s.Gain = newValue;    // modifies LOCAL COPY only—not stations[i]!
```

Mutable structs also make thread-safety analysis harder because copies can hide whether the actual data was modified — dangerous when combined with P7.C1 race condition on shared arrays between audio and main threads.

## Impact
- Bug pattern where code reads struct field from array, modifies in local variable expecting change to propagate silently fails (zero compiler warning)
- Conflicts badly with C# immutability best practices; every mutation requires explicit awareness of value-type semantics

## Recommended Fix
1. Add `readonly` to all fields that shouldn't change after construction:
```csharp
public readonly struct StationState {   
    public readonly float Gain;  // immutable by-design       
}  
```
2. If mutation IS needed, force callers through explicit methods rather than direct field assignment on structs. Note: for stationary state the array must stay mutable — but individual station structs should be value objects not containers of mutability leaking elsewhere in caller codebase since they're stored inside arrays accessed concurrently on multiple threads already per issue P7.C1 above!

## Verification
- Compiler errors on any direct-field mutation attempt → must call `SetX()` method or assign new struct to array element explicitly (e.g. `stations[i] = station with { Gain = newVal }`)
- Existing navigation behavior unchanged after refactor (no silent logic breakage from new readonly constraints)
