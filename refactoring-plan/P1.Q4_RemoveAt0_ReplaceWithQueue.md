# P1.Q4_O_n2_RemoveAt_ReplaceWithQueue

**Приоритет:** P1-Major  
**Область:** UI / Performance — wrong data structure for FIFO buffer
**Статус:** Новый документ, не задокументировано  

---

## Описание проблемы

`SignalRichTextFormatter.TrimEntries()` (Source/UI/SignalRichTextFormatter.cs:69-78) использует `List<SignalEntry>` и многократно вызывает `.RemoveAt(0)` внутри while-loop для удаления oldest entries когда signal buffer превышает MaxSignalEntries (60) или morseCharCount свыше MaxMorseChars (20). Это textbook пример FIFO queue, реализованный неверным данными.

```csharp
// SignalRichTextFormatter.cs: строки 69-78
public static void TrimEntries(List<SignalEntry> entries, ref int morseCount) {
    while ((morseCharCount > MaxMorseChars || entries.Count > MaxSignalEntries) 
           && entries.Count.IsPositive())                                               
    {                                                                                 
        if (entries[0].Type != SignalCharType.Separator)                             
            morseCharCount--;                                                        
        entries.RemoveAt(0);                                                        // ← O(n) за вызов из-за Array.Copy
    }                                                                                 
}  
```

`List<T>.RemoveAt(0)` выполняет `Array.Copy` внутренно сдвигая все оставшиеся элементы для заполнения пропуски. Вызывая это внутри while-loop который может итерироваться до 60 раз: Call #1 сдвигает 59 элементов, Call#2 — 58... worst case = Σ(n-k) ≈ n*(n-1)/2 total element copies per trim burst. Для MaxSignalEntries=60 это ~1770 копирований элементов за один burst — tiny но unnecessary когда `Queue<T>` с .Dequeue() даёт O(1) удаление front элемента без allocation churn.

Caller из `SonneController.cs:30` уже владеет буфером:
```csharp  
private readonly List<SignalEntry> signalEntries = new List<SignalEntry>();

// OnStationElementCompleted вызывает TrimEntries(signalEntries...) каждый тик:
OnStationElementCompleted → SignalRichTextFormatter.TrimEntries(signalEntries, ref morseCharCount) → SonneController.cs:146
OnStationSequenceFinished → TrimEntries(signalEntries, ref morseCharCount) → SonneController.cs:167
```

Также `SonneController.cs` строки 226-230 делают ClearSignalBuffer() — полный clear списка + reset счётчика. При Queue<T> чистый `.Clear()` тоже сбрасывает внутренний head pointer эффективнее.

## Рекомендуемое решение 

1. Заменить `List<SignalEntry>` → `Queue<SignalEntry>(capacity: MaxSignalEntries)` в SonneController.cs строка 30
2. Обновить вызовы TrimEntries или сделать перегрузку для Queue<T>-compatible API
3. Если Peek + conditional Dequeue tricky с Queue (Peek не dequeue), использовать simple head pointer int вместо List — híbrидный подход даёт O(1) amortized performance без full compaction каждый раз  

## Альтернатива: гибридный индекс

```csharp
// Hybrid approach: сохранит indexing semantics если нужно позже
private struct SignalBuffer {
    private readonly SignalEntry[] buffer = new SignalEntry[MAX_SIZE];
    private int headIndex;  // всегда точка oldest entry
    
    public void Enqueue(SignalEntry e) => /* circular buffer logic */;
    public SignalEntry Dequeue() => buffer[headIndex++ % MAX_SIZE];
    public int Count => ...;  // вычисляется из capacity
}
```
